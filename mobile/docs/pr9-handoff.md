07.09.2026. Исходная версия Ильи / ShmelJUJ — `30005a6`.
Первое поведенческое исправление — **`fba79ce`**; поверх него по уточнению `vxofi`

## Самое важное перед запуском

1. **Твой интерфейс остаётся базой.** Ассеты, общие компоненты, сетки, стили,
   навигационные вкладки, раскрытие Кухни, экран убранства и две кнопки рецепта
   сохранены. Нет новых экранов оплаты/доставки/адресов внутри игры.
2. Изменены обработчики, доступность и согласованные подписи **четырёх экранов**,
   состояние в `DemoContext`; добавлен один интерфейс внешнего оформления.
   Backend, recommender, зависимости и lockfile относительно `30005a6` не менялись.
3. **Полный demo-flow работает после обычного запуска backend и mobile.**
   Нижняя кнопка «К оформлению» одним нажатием моделирует внешнюю покупку через
   встроенный demo-обработчик. Синтетический чек проверяет настоящий backend,
   потом товары появляются на Кухне. Не нужно отдельно сохранять план/отправлять
   чек, подключать приложение магазина, ставить флаг или вводить команды в консоли.
4. **Перед нажатием явно видно «Демо: оформление и покупка моделируются».**
   После успешного ответа — «Демо-покупка подтверждена». Рекомендации, проверки,
   прогресс и XP работают нашим кодом; только внешняя покупка синтетическая.
   Промежуточный вариант «оформление не подключено» из `fba79ce` пересмотрен:
   его **не нужно показывать на защите**. Это не задача тебе писать доставку.
5. До мержа собственной вечерней полировки обнови локальную ветку. Не заменяй
   новые обработчики целиком старым `DemoContext` ради возврата внешнего вида:
   для оформления достаточно править JSX/стили с сохранением вызовов ниже.

## Как теперь читать состояние

| Ситуация | Ожидаемое поведение |
|---|---|
| Выбираем товары, уходим на Кухню/в выдачу и возвращаемся к тому же блюду | Черновик сохраняется автоматически в сессии; POST плана ради каждого выбора нет. |
| Явно выбрали другое блюдо | Оно заменяет текущий игровой черновик. Это не история нескольких планов и не замена всей магазинной корзины. |
| Нажали «К оформлению» в обычной сборке PoC | Включённый по умолчанию demo-обработчик моделирует покупку. Чек проходит реальный API; при успехе пополняется Кухня. |
| Приложение подключено | Внутренне фиксируем offer/план/состав, передаём снимок в `openCheckout`. Пользователю не нужно отдельно сохранять план. |
| Приложение подтвердило отмену без покупки | Выбранные товары остаются редактируемыми; покупки/XP нет. Уже созданное серверное задание остаётся в статистике созданных планов, не покупок. |
| Ответ потерян, исход операции неизвестен | Состав попытки заблокирован. Повтор использует тот же checkout/plan ID. Если потерян ответ на чек, повторяем чек, не заказ. |
| Принят подходящий чек для cook | Кухня → «Готовить» → «Я приготовил». Сам чек ещё не завершает готовку. |
| Принят подходящий чек для ready | Задание завершается без готовки. На Кухне — переход к прогрессу. |
| Всё уже есть | Быстрый старт готовки без оформления/нового чека. Право на XP всё равно проверяет сервер. |

Доставка и уценка — текущие demo-настройки по умолчанию. Full-price вариант
не запрещён. Готовый товар должен поддерживать текущий способ получения:
товар только для визита не выбирается для доставки. Общий список API может
содержать оба типа, поэтому `product_options[0]` не заменяет `readyProduct`.

Сохранение черновика **не означает хранение после закрытия приложения**.
Смена синтетического профиля сбрасывает сессию; чужие поздние ответы отбрасываются.
Предметы убранства по-прежнему локальные; мы не подключали старый серверный
каталог обоев поверх твоего нового каталога.

Покупка ингредиентов сама по себе даёт **0 XP до готовки**. После «Я приготовил»
сервер может начислить 20 XP; покупка ready завершает задание сразу. Второго
бонуса за тот же покупочный день нет. Рецепт из имеющихся покупок позволяет
показать готовку без нового заказа, но это не доказательство дополнительной покупки.

## Как проверить на своей машине

После обновления ветки, из `mobile`, с Node 24 и установленными зависимостями:

```sh
npm run typecheck
npm test
npm run test:api
X5_TEST_ENGINE=model npm run test:api
npm run web -- --clear
```

API-тестам нужен Python проекта: `.venv` в корне либо `X5_TEST_PYTHON` с путём
к интерпретатору. Backend и `EXPO_PUBLIC_API_BASE_URL` для web/телефона — по
[README](../README.md#запуск). На телефоне `localhost` означает сам телефон.
Зависимости в этом исправлении не менялись; переустановка не обязательна, если
текущая установка соответствует lockfile.

Короткая ручная проверка:

1. «Рецепты» → «Спагетти болоньезе» → «Выбрать товары». Уценка лука видна;
   выбрать обычный лук, уйти на Кухню → «Мой план»: выбор не сброшен.
2. Перед «К оформлению» видна подпись деморежима. Нажать кнопку: после принятого
   чека появляется подтверждение, продукты добавляются на Кухню. Кухня →
   «Готовить» → «Я приготовил» → прогресс. Дополнительного подключения нет.
3. «Паста с томатами», если всё есть → готовить → «Я приготовил». Без новой
   покупки доступны шаги/результат; награда зависит от подтверждённого исходного
   чека и лимита его дня. Не обещаем XP за любую отметку.
4. Выбрать болоньезе заново → «Купить готовое» → «К оформлению»: задание
   завершается без готовки. Если бонус этого покупочного дня уже использован,
   XP больше не прибавляются. На Кухне доступен «Мой прогресс».
5. Профиль → другой синтетический покупатель → обратно: нет чужих планов,
   уценка не пропадает. Проверить панель кухни, прокрутку и экран убранства.

Для автоматической проверки **обычного встроенного деморежима**:
[browser smoke и требования](../../docs/commerce-host.md#как-проверять-и-демонстрировать).
Он headless, требует Playwright и чистый backend, нажимает обычные кнопки без
подстановки host/чеков из теста. Playwright не нужен для ручного показа в Expo Go.
Физический телефон не проверялся; надо проверить связь с backend по LAN.

Приёмка встроенного demo: **88 клиентских тестов, 18 API-тестов на каждом движке**,
TypeScript, экспорт web/iOS/Android, browser smoke 390×844 без подстановки host.
Полный backend pytest прошёл на первом исправлении `fba79ce`; backend с тех пор
не менялся и повторно проверяется GitHub перед merge.
CI относится к **конкретному HEAD PR**: старый красный mobile-check
от `30005a6` не является результатом нового кода. Полный browser smoke в CI
пока не включён; там идут client/API-тесты и экспорт.

## Как забрать обновление, не потеряв вечернюю полировку

История твоих коммитов сохранена. Ветка PR обновляется обычным fast-forward,
без force-push. На нашей стороне dirty ML/research-файлы в него не включены.

Сначала `git status --short`. Если есть незакоммиченная полировка — сохрани её
отдельным коммитом в своей ветке или сделай резервную копию; не применяй reset.
Далее для чистой локальной ветки:

```sh
git fetch origin
git switch feat/mobile-polish
git merge --ff-only origin/feat/mobile-polish
```

Если `--ff-only` отказался, это может означать твои новые локальные коммиты,
а не поломку. Посмотреть расхождение:

```sh
git log --oneline --left-right HEAD...origin/feat/mobile-polish
```

При наличии собственной полировки её нужно свести обычным merge, сохраняя
обе стороны. Не переписывать историю и не возвращать весь экран старой копией.
Новый PR с полировкой после слияния #9 должен включать обновлённую базу `main`.

## Если что-то выглядит не так

- **Видишь старое «Оплатить и получить 20 XP».** Проверь commit/ветку, останови
  старый Expo и запусти с `--clear`. На локальных worktree воспроизведён старый
  кэш сборщика; после очистки новая версия прошла smoke.
- **Кнопка готового отключена.** Проверь `readyProduct`, fulfillment, `editable`
  и pending-попытку; не обходи guard без выяснения причины.
- **После ошибки товары нельзя менять.** Для неопределённой попытки это защита
  от подмены состава при повторе. После подтверждённой отмены редактирование
  возвращается; если не вернулось — это регрессия.
- **Упала проверка исходников после твоей согласованной полировки.** Не нужно
  подгонять интерфейс под старый тест. Обновить baseline под новый согласованный
  визуал и отдельно сохранить поведенческие проверки; не удалять тест целиком.
- **Нужен быстрый разбор регрессии.** Пришли HEAD, профиль, путь из 2–3 действий,
  ожидаемый/фактический результат и ошибку API. Изолируем проблемный обработчик;
  твои ассеты/раскладка не требуют отката вместе с ним.

Первый diff исправлений: `git show fba79ce -- mobile/src`.
Для всей интеграции: `git diff 30005a6..origin/feat/mobile-polish -- mobile/src`.
Встроенный demo-режим — часть обновляемого PR, не отдельная будущая задача.
Он не означает реальную оплату, доставку или доказанный рост покупок.
