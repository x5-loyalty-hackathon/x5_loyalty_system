# Рецепты food.ru и готовая еда: офлайн-снимок для PoC

Задача: дополнить `recsys/data/ready_food_catalog.json` рецептами с названием,
составом, рейтингом и доступными комментариями. Все результаты — статические
файлы в `recsys/data/foodru/`. Обращения к food.ru выполняет только отдельная
команда `collect`; команда `build` работает без сети.

Исходный каталог содержит 601 товар Москвы, ключ — **`chain:plu`**, не название
и не один `plu`. Снимки X5: `2026-09-04T22:52:34+00:00` и
`2026-09-04T23:38:22+00:00`. В нём есть также соусы, консервы и выпечка;
все исходные строки сохранены в обогащённом файле.

Сначала собраны 700 кандидатов по карте сайта. После проверки правил проведён
дополнительный поиск по товарам без принятой пары: ещё 144 новых адреса с

локального кэша и результаты объединены одной командой сборщика. Список
`recipe_urls.txt` фиксирует именно этот итоговый набор.

Просмотр названий принятых пар и отдельных составов выявил и помог исправить
ошибки «масло → мясо» при транслитерации, «куриное яйцо → куриное мясо»,
«рыбная намазка → макароны», «блины без начинки → блины с начинкой»,
«рис → рисовая лапша», «овощной/сырный салат → салат с курицей» и
«картофель внутри котлеты → картофельный гарнир». Эти случаи покрыты тестами.
Отдельного независимого аудита точности всех 244 пар не проводилось.

Остальные 357 товаров **не получили состав по автоматическому матчингу**;
их строки остаются в каталоге. `review.csv` показывает кандидатов и причины,
поэтому расширение покрытия можно продолжить адресно, не пересобирая весь сайт.

## Файлы

| Файл в `recsys/data/foodru/` | Содержимое |
|---|---|
| `recipes.json` | Рецепты `foodru_<id>`, ингредиенты с количествами, рейтинг, комментарии, URL и дата получения |
| `matches.json` | По строке на товар: статус, принятый рецепт или `null`, до трёх кандидатов с причинами проверки |
| `enriched_catalog.json` | Исходные поля всех товаров + `foodru_match`, `assumed_ingredients`, `ingredient_provenance` |
| `ready_meal_options.json` | Принятые пары в форме исследовательского `ReadyMealOption` |
| `review.csv` | Все товары и кандидаты для просмотра в таблице, UTF-8 с BOM |
| `recipe_urls.txt` | Адреса собранных рецептов для повторного сбора того же набора |
| `summary.json` | Покрытие, полнота отзывов, ошибки и контрольные суммы входных файлов |

Пример чтения статического mock:

```python
import json
from pathlib import Path

root = Path("recsys/data/foodru")
recipes = json.loads((root / "recipes.json").read_text())["recipes"]
products = json.loads((root / "enriched_catalog.json").read_text())["products"]
recipes_by_id = {recipe["recipe_id"]: recipe for recipe in recipes}

for product in products:
    if product["foodru_match"]["status"] == "matched":
        recipe = recipes_by_id[product["foodru_match"]["recipe_id"]]
        print(product["name"], recipe["title"], product["assumed_ingredients"])
```

## Получение и воспроизводимость

Сборщик использует стандартную библиотеку Python 3.11+. Установка браузера,
платные API и авторизация не требуются.

```bash
# Пересчитать матчинг из уже сохранённых JSON: сеть не используется.
.venv/bin/python -m recsys.offline.foodru build

# Обновить рецепты по сохранённому списку; HTML из кэша используется повторно.
.venv/bin/python -m recsys.offline.foodru collect \
  --urls recsys/data/foodru/recipe_urls.txt

# Действительно свежий снимок того же набора: отдельный кэш и output.
.venv/bin/python -m recsys.offline.foodru collect \
  --urls recsys/data/foodru/recipe_urls.txt \
  --cache artifacts/foodru-refresh/cache --output artifacts/foodru-refresh/result

# Заново найти кандидатов под каталог через карту сайта.
.venv/bin/python -m recsys.offline.foodru collect --rediscover \
  --per-product 2 --max-recipes 700

# Проверки без сетевых запросов.
.venv/bin/python -m pytest tests/test_foodru_offline.py
```

При завершении задачи проверки сборщика, существующих пар готовой еды и границ
исследовательского контура прошли: **63 passed** (`test_foodru_offline.py`,
`test_recsys_ready_food_pairs.py`, `test_recsys_merge_boundaries.py`). Повторный
`build` с другим `PYTHONHASHSEED` дал побайтно одинаковые файлы; контрольные
суммы входного каталога и снимка рецептов проверены.

Сбор ограничен тремя потоками и **одним началом HTTP-запроса в секунду суммарно**.
Повторные запуски используют сжатый HTML-кэш и сохранённый план
`artifacts/foodru/discovery.json`. `--rediscover` пересчитывает план;
`--per-product` и `--max-recipes` применяются при его создании, а не к уже
сохранённому плану. Сначала выбирается лучший кандидат каждого товара, затем
вторые кандидаты, с общим ограничением размера набора. Поиск по транслитерации
URL — лишь этап отбора страниц; окончательный матчинг использует настоящее
название и состав карточки.

Кэш, карты сайта и промежуточный `collection_progress.json` находятся в
игнорируемом Git каталоге `artifacts/`. Ошибки запросов/парсинга сохраняются
в `recipes.json.errors`. Финальный снимок публикуется после завершения сбора;
при прерывании повторный запуск дочитывает кэш. При ошибке разбора сохранённую
страницу можно проверить по URL в соседнем JSON кэша. Для повторной загрузки
такой страницы следует удалить соответствующие `.html.gz` и `.json` из кэша
либо использовать отдельный кэш.

`build` детерминирован при одинаковых JSON, версии правил и ручных поправках.
Контрольные суммы связывают результаты с исходным каталогом и снимком рецептов.
Повторный **сетевой** сбор может изменить рейтинги, комментарии и состав.

## Правила матчинга

1. Удаляем известные бренды, вес упаковки и обозначения заморозки; учитываем
   `ё/е`, транслитерацию, склонения и небольшой явный словарь синонимов.
2. По взвешенному пересечению слов выбираем кандидатов. Редкие слова имеют
   больший вес. `score` — эвристика сходства, **не вероятность правильного матча**.
3. Проверяем семейство блюда, явно названные компоненты и дополнительные
   компоненты в названии рецепта. Противоречащие варианты мяса отсеиваются.
   Наличие куриного яйца или бульона не подтверждает куриное мясо.
   Сохранённый X5 `dish_type`, когда он достаточно конкретен, может отклонить
   противоречащую пару. Овощной/сырный салат не получает скрытое куриное мясо
   из рецепта с общим названием.
4. У блюд с гарниром отдельно проверяем, что рецепт тоже называет этот гарнир.
   Рыбная паста-намазка не проходит как макароны; «без сахара» и «без начинки»
   не получают явно противоречащий состав.
5. Автоматически принимается кандидат с `score >= 0.72` без причин проверки.
   При отсутствии распознанного семейства допускается только совпадение всех
   нормализованных слов названия. Рейтинг может разрешить ничью среди одинаково
   подходящих названий, но не оправдывает другое блюдо.

Статусы:

- `matched`: выбран один рецепт; его состав перенесён как допущение для PoC.
- `review`: кандидаты есть, но правила не подтвердили соответствие;
  `recipe_id` и `assumed_ingredients` остаются `null`.
- `unmatched`: кандидат не найден либо пара отклонена ручной поправкой.

Это эвристический, просмотренный на примерах матчинг без независимой разметки
точности. Даже статус `matched` не доказывает идентичность рецептуры производителя.
Разные готовые товары могут ссылаться на один рецепт. Среди кандидатов могут
быть несколько почти одинаковых рецептов food.ru; стабильный ключ — ID источника.

Ручные решения можно применить без правки кода и исходных товаров:

```json
{
  "perekrestok:2157530": {
    "recipe_id": null,
    "reason": "После просмотра состава отклонено соответствие"
  }
}
```

```bash
.venv/bin/python -m recsys.offline.foodru build --overrides path/to/overrides.json
```

Для принятия пары указывается существующий `foodru_<id>`. Непустой `reason`
обязателен; неизвестные товары и рецепты считаются ошибкой. Ручная поправка
сохраняется в результате. При следующих сборках следует передавать тот же файл.

## Состав, рейтинг и отзывы

Источник состава — опубликованное в HTML состояние `__NEXT_DATA__` и запасной
вариант JSON-LD `Recipe`. В первом случае сохраняются название ингредиента,
ID продукта food.ru, единица, количество, вес в граммах и группа
«Для блюда»/«Для подачи». ID ингредиента food.ru **не является PLU X5**.
Для «по вкусу» и «по желанию» количество и вес — `null`, а не выдуманный ноль.
При запасном разборе JSON-LD сохраняется исходная строка без угадывания единиц.

Количества относятся ко **всему рецепту с указанным выходом**, не к упаковке X5.
У `ingredient_provenance` всегда `kind=recipe_name_proxy`,
`manufacturer_verified=false`, URL рецепта и
`quantities_scope=whole_recipe_not_retail_package`.
Из этого состава нельзя выводить подтверждённые аллергены или точное КБЖУ SKU.

Рейтинг рецепта хранится отдельно от товара: `value`, `count`, `best`.
Отсутствующий рейтинг/ноль голосов — `null`. Комментарии сохраняются как текст,
дата и ID комментария; имена, профили, пользовательские ID/X5 ID не копируются.
Комментарии и агрегированный рейтинг — разные сущности: оценок обычно больше.

Собираются комментарии, присутствующие в HTML карточки, обычно первая страница
до 10 штук. Скрытые API и пагинация комментариев не вызываются:

- `complete`: число собранных комментариев достигло указанного страницей total;
- `partial`: комментарии есть, но их меньше total или total неизвестен;
- `not_exposed`: в разобранном HTML нет комментариев; это **не утверждение,
  что отзывов вообще не существует**.

## Граница с текущим PoC

`ready_meal_options.json` валидируется исследовательским контрактом
`recsys.experimental.contracts.ReadyMealOption`. В нём новые ID `foodru_<id>`,
ссылки разрешаются в соседнем `recipes.json`. Это не замена существующих
`bliny`, `borsch` и остальных ID из `recsys/recipes.py`.

Сырые рецепты сохраняют весь состав источника, включая ингредиенты за пределами
текущего малого `recsys.catalog`. Поэтому `recipes.json` — схема данных источника,
а не готовый `app.contracts.Recipe`. Для подключения к ранжированию потребуется
явно сопоставить ингредиенты с его каталогом. Автоматически объявлять собранные
рецепты `verified=True` и менять замороженный обучающий пул нельзя.

Этот сборщик не изменяет `ready_food_pairs.py`, API, мобильные mock и модель.
Онлайн-интеграций с food.ru или базой X5 не добавлено. Подключение статических
файлов в нужный сценарий допускается без сетевых запросов.
