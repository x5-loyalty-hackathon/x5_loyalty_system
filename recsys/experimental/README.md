# Исследовательский контур, не HTTP API

Источник: `experiment/recsys-benchmark@02132c8`, попавший в `main@372de69`
через PR #8. При интеграции 06.09.2026 его несовместимые с API 1.2 типы и
политики сохранены здесь. Это слой воспроизводимости экспериментов, **не второй
backend для мобильного приложения**. Продуктовые решения ADR-001–004 не меняются.

## Зачем разделение

В стенде есть `RankingPolicy`, вероятностное наличие дома, `price_is_estimate`
и пары с готовой едой из снимка каталога. Эти объекты нужны для проверки гипотез,
но не заменяют согласованные HOME, одну точку, full-basket opt-in и проверку
готового SKU по остатку/сроку/составу. Старый стенд не оценивает конечную
meal-выдачу API 1.2; его числа нельзя переносить на приложение.

## Карта

| Рабочий PoC | Воспроизведение исследовательского стенда |
|---|---|
| `app/contracts.py`, `app/service.py`, `app/safety.py` | `recsys/experimental/contracts.py`, `service.py`, `safety.py` |
| `recsys/model.py`, `profiles.py`, `inventory.py`, `pantry.py` | Одноимённые модули в `recsys/experimental/` |
| `recsys/catalog_freeze.py` — 37 обучающих API-рецептов | `recsys/experimental/catalog_freeze.py` — исходное JSON-представление и его хеш |
| `recsys/evaluation.py` — прежняя диагностика runtime scorer | `recsys/experimental/evaluation.py` — метрики исходного ML-стенда |

Ингредиенты, цены, рецепты, metadata, JSON-данные и `_logistic` **не копируются**.
`experimental/recipes.py` преобразует общий каталог в исходную исследовательскую
схему. Остальные модули здесь — сохранённые версии несовместимой логики с
переписанными импортами; отдельные версии нужны для неизменности экспериментальных
предпосылок. Они не должны развиваться как вторая продуктовая система.

CLI стенда остаются на прежних путях: `recsys.benchmark`, `recsys.panels`,
`recsys.experiment1_ranker_quality`, `recsys.experiment2_service_logic`,
`recsys.experiment3_catalog_coverage`, `recsys.human_eval`, `recsys.split_audit`.
Их импорты указывают на этот контур. Генератор примеров `recsys.generate_examples`
по-прежнему создаёт **API 1.2**, не старые исследовательские ответы.

## Как проверять и продолжать

Из корня репозитория:

```bash
.venv/bin/python -m pytest
.venv/bin/python -m pytest tests/test_recsys_merge_boundaries.py
.venv/bin/python -m recsys.experimental.evaluation
```

Общий pytest включает исходные тесты ML-ветки с заменой импортов; исследовательский
fixture называется `experimental_ml_engine`, runtime — `ml_engine`. Новые проверки
границ воспроизводят четыре закоммиченных манифеста **без записи файлов** и проверяют,
что API с настоящей моделью не импортирует `recsys.experimental`.

Числа в старых отчётах сохранены как история: даже воспроизведение входных данных
не доказывает качество на людях или uplift. Holdout не используется здесь для
выбора модели; ответы людей и платные LLM-вызовы не генерируются.

Следующий перенос методики оценки на API 1.2 должен явно использовать
`app.service` и финальный ответ после safety/selector, фиксировать новую версию
эксперимента и не перезаписывать старые манифесты/отчёты под теми же числами.
После такого переноса ненужную совместимость можно удалить отдельным PR.
