# Как собрать мобильное демо «X5 Домовой» с настоящим backend

- **Статус:** исходный UX-план ветки `feat/mobile-demo`, синхронизирован с
  meal-контрактом 04.09.2026.
- **Owner:** Product/UX & Frontend.
- **Контракт API 1.2:** [ADR-003](decisions/003-challenge-mode-selection.md),
  [ADR-004](decisions/004-recipe-book-and-shopping-context.md),
  [technical design](technical-design.md), схемы в `app/contracts.py`.

**Обновление 05.09:** интерфейс `feat/mobile-app` перенесён и адаптирован в
`experiment/vxofi`. Актуальный результат, границы и проверки —
[план интеграции](mobile-integration-plan.md) и [запуск](../mobile/README.md).
Ниже — исходная схема экранов, не отчёт о фактически проверенном UI.

Цель — сделать четыре связанных экрана, которые открываются на iPhone через
Expo Go и обращаются к уже существующему FastAPI на Mac. Публиковать приложение
в App Store, настраивать TestFlight, авторизацию и базу данных для демо не нужно.

```text
iPhone: React Native + Expo Go
            ↓ HTTP/JSON через Wi-Fi
Mac: FastAPI + recommender + in-memory state
```

## Шаг 1. Сначала нарисовать четыре макета

Создай в Figma четыре фрейма одного размера, например `393 × 852`.

### Экран 1 — «После покупки»

Что показать:

- Домового и несколько продуктов из последнего чека;
- одну основную карточку челленджа и до двух релевантных альтернатив;
- режимы `Из корзины`, `Повторить`, `Попробовать новое` без искусственного
  заполнения всех трёх;
- рекомендованный способ `Приготовить` или `Без готовки` и короткое объяснение;
- количество недостающих ингредиентов;
- выбранный контекст покупки (`Дом`, `Работа`, `Рядом` или сохранённое место),
  без обязательной передачи текущей геолокации;
- кнопку выбора рецепта.

Этот экран будет получать данные через:

```text
POST /api/v1/meal-recommendations
```

Источник порядка — `challenge_selection`: первая карточка соответствует
`default_mode`, остальные режимы берутся из `available_modes`. Если mode входит
в `explicit_choice_required`, UI показывает opt-in («Собрать новое блюдо с
нуля?»), но не оформляет его как автоматически выбранный челлендж.

### Экран 2 — «Рецепт»

Что показать:

- название и время приготовления;
- объяснение, почему выбран рецепт;
- переключатель `Приготовить / Без готовки`, только когда доступны оба route;
- для `Приготовить` — список ингредиентов и состояния `куплено`, `есть дома`,
  `уценка`, `обычная цена`;
- для `Без готовки` — подходящее тому же блюду готовое предложение;
- предупреждение, что уценённый товар не забронирован;
- кнопку `Сохранить рецепт`, вызывающую `POST /api/v1/saved-recipes` без XP;
- кнопку `Добавить в план`.

Отдельный запрос здесь не нужен: экран использует `cook_variant` и
`ready_variant` выбранной рекомендации из ответа первого endpoint. Если один
route не прошёл safety/availability, пустой переключатель не показывается.

### Экран 3 — «Мой план»

Что показать:

- выбранные недостающие товары либо выбранное готовое блюдо;
- одну выбранную точку и расстояние от активного `shopping_context`;
- возможность выбрать другую точку из `store_selection.options`; варианты с
  `complete=false` нельзя оформлять как полную корзину;
- итоговую экономию;
- выбор `Доставка` или `Следующий визит`;
- кнопку `Сохранить план`, отправляющую `POST /api/v1/meal-plans`;
- после успешного сохранения — кнопку demo-подтверждения следующего чека.

Выбор доставки входит в запрос сохранения плана как `fulfillment`; настоящий
checkout доставки в PoC не реализуется.

### Экран 4 — «Кухня Домового»

Что показать:

- завершённое блюдо и route `Приготовил` или `Взял готовое`;
- XP и уровень Домового;
- количество завершённых рецептов;
- фактическую экономию;
- число купленных rescue-позиций;
- личную позицию без публичного списка пользователей.

Для `ready` перед показом этого экрана приложение отправляет чек с
`meal_plan_id`:

```text
POST /api/v1/events/receipts
```

А актуальное состояние получает через:

```text
GET /api/v1/progress/user_meal_demo_001
```

Для `cook` чек сначала переводит план в `collected`, затем требуется отдельное
подтверждение:

```text
POST /api/v1/meal-plans/{plan_id}/complete-cook
```

## Шаг 2. Зафиксировать один демонстрационный маршрут

Не пытайся реализовать все возможные состояния. Для защиты нужен один стабильный
happy path:

```text
открыть приложение
→ получить один основной челлендж и доступные альтернативы
→ увидеть, почему выбран тип «Из корзины»
→ выбрать «Овощной омлет»
→ увидеть рекомендованный route и объяснение
→ при наличии переключиться между «Приготовить» и «Без готовки»
→ сохранить рецепт и увидеть его в режиме «Повторить» при следующем запросе
→ сохранить выбранный продукт и следующий визит
→ подтвердить новый synthetic-чек
→ увидеть завершённое блюдо, кухню и обновлённый прогресс
```

Referral лучше оставить небольшой дополнительной кнопкой на последнем экране.
Он не должен мешать основному сценарию.

## Шаг 3. Подготовить графику

Из макетов экспортируй:

- четыре позы Домового в PNG;
- при необходимости фон кухни;
- небольшие изображения ингредиентов;
- иконки только тех действий, которые реально присутствуют в демо.

Для первой версии не экспортируй экран целиком картинкой. Текст, кнопки и
карточки лучше собрать обычными компонентами React Native, а PNG использовать
только для персонажа и иллюстраций.

## Шаг 4. Проверить backend на Mac

В корне backend-проекта создай и активируй Python-окружение, если этого ещё не
сделано:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[dev]'
```

Проверь тесты:

```bash
python -m pytest
```

Запусти API так, чтобы он был доступен не только самому Mac, но и iPhone:

```bash
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

Не закрывай это окно терминала во время работы приложения.

## Шаг 5. Узнать локальный IP-адрес Mac

В другом окне терминала выполни:

```bash
ipconfig getifaddr en0
```

Например, команда может вернуть:

```text
192.168.1.20
```

Проверь backend с iPhone. Открой Safari и введи:

```text
http://192.168.1.20:8000/health
```

Если появляется ответ со статусом `ok`, iPhone видит Mac и можно переходить к
frontend.

Если страница не открывается:

1. проверь, что Mac и iPhone находятся в одной Wi-Fi-сети;
2. разреши входящие подключения для Python в настройках firewall macOS;
3. проверь, что Uvicorn запущен именно с `--host 0.0.0.0`;
4. в публичной сети попробуй подключить Mac к точке доступа iPhone.

## Шаг 6. Создать приложение Expo

Установи на iPhone приложение **Expo Go** из App Store.

На Mac перейди в папку, где будет находиться frontend, и выполни:

```bash
npx create-expo-app@latest mobile
cd mobile
npx expo start
```

Expo покажет QR-код. Отсканируй его камерой iPhone и открой проект через Expo
Go. Во время разработки изменения будут автоматически появляться на телефоне.

## Шаг 7. Создать минимальную структуру frontend

Для демо достаточно такой структуры:

```text
mobile/
├── src/app/
│   ├── index.tsx
│   ├── recipe.tsx
│   ├── plan.tsx
│   └── kitchen.tsx
├── src/components/
│   ├── Domovoi.tsx
│   ├── RecipeCard.tsx
│   └── IngredientRow.tsx
├── src/lib/
│   └── api.ts
└── assets/
    └── domovoi/
```

Назначение файлов:

- `index.tsx` — экран после покупки и список рекомендаций;
- `recipe.tsx` — выбранный рецепт;
- `plan.tsx` — товары и способ получения;
- `kitchen.tsx` — итоговый прогресс;
- `api.ts` — все обращения к FastAPI;
- `components` — повторяемые визуальные элементы.

Для переходов используй Expo Router, который входит в стандартный проект Expo.
Redux, Zustand и другую библиотеку состояния для четырёх экранов подключать не
нужно. Выбранный рецепт можно передать параметром маршрута либо сохранить в
простом React Context.

## Шаг 8. Настроить адрес backend

В `src/lib/api.ts` задай адрес Mac:

```ts
export const API_BASE_URL = "http://192.168.1.20:8000";
```

Подставь IP, который вернула команда `ipconfig`. Не используй `localhost`:
для приложения на iPhone это будет сам iPhone, а не Mac.

Собери в этом файле функции основного flow:

```text
getHealth()
getMealRecommendations(payload)
saveRecipe(payload)
getSavedRecipes(userId)
saveMealPlan(payload)
submitReceipt(payload)
completeCookPlan(planId, payload)
getProgress(userId)
```

Дополнительный вызов `evaluateReferral(payload)` можно добавить после готовности
основного сценария.

## Шаг 9. Подключить первый экран к рекомендациям

Возьми содержимое backend-файла `examples/meal_recommendation_request.json` как
демонстрационный payload. Его можно временно хранить во frontend как обычный
TypeScript-объект. Legacy endpoint `/api/v1/recommendations` оставлен для
совместимости, но новый UI строится по meal-контракту.

При открытии первого экрана либо по кнопке `Разобрать чек`:

1. покажи состояние загрузки;
2. отправь payload в `POST /api/v1/meal-recommendations`;
3. сохрани массив `recommendations`;
4. отрисуй карточки рецептов;
5. при ошибке покажи кнопку `Повторить`.

До отрисовки проверь:

1. `challenge_selection.default_mode` — основной режим;
2. `mode_reason_codes[default_mode]` — объяснение его выбора;
3. `explicit_choice_required` — режимы, которые нельзя выбирать автоматически;
4. `recommendations` — в начальном ответе максимум один представитель mode.

`available_modes` и `explicit_choice_required` уже приходят в стабильном
порядке. Не сортируй их повторно и не показывай сырые идентификаторы reason
codes: отображай только заранее заданный UI-текст для кодов из публичного
реестра. Поле верхнего уровня `warnings` не используется как debug-console и
не содержит внутренних recipe/SKU ID.

Нажатие на альтернативный режим может повторно вызвать endpoint с
`requested_mode`. Такой ответ уже является каталогом внутри явно выбранного
режима и может содержать несколько рецептов одного mode. Выбор карточки
открывает экран блюда и передаёт его `meal_id`.

## Шаг 10. Подключить экран рецепта

На экране блюда отобрази данные из `MealRecommendation`:

- `title`;
- `mode`;
- `reason_codes`;
- `default_route`, `available_routes` и `route_reason_codes`;
- `cook_variant` и/или `ready_variant`;
- `warnings`.

Поле `ingredients[].required` отличает обязательные ингредиенты от гарнира:
только обязательные позиции учитываются при решении, является ли `explore`
полной новой корзиной.

Для route `cook` варианты товаров лежат **внутри каждого ингредиента**:

```text
recommendations[i].cook_variant.ingredients[j].source
recommendations[i].cook_variant.ingredients[j].product_options
```

Все эти `product_options` относятся к
`recommendations[i].cook_variant.store_selection.selected_store_id`.
`store_selection.reason_codes` объясняет автоматический выбор, а `options`
показывает coverage альтернатив. Для выбора дома или работы измени
`shopping_context.anchor_type/anchor_id`; для ручного выбора магазина повтори
запрос с `shopping_context.selected_store_id`. `distance_km` уже рассчитан
относительно выбранного anchor, frontend не должен считать его от адреса.

Для route `ready` готовые товары находятся здесь:

```text
recommendations[i].ready_variant.product_options
```

`ProductOption` содержит `name`, `price`, `original_price`, `store_id`,
`distance_km`, `expires_at` и `fulfillment_options`. У ready-варианта также есть
`meal_intent_id` и `contained_categories`; это соответствие уже проверено
backend safety-гейтом.

Не придумывай отдельную структуру данных под макет. Лучше сразу подписать
элементы Figma теми сущностями, которые реально возвращает API.

Кнопка `Добавить в план` переводит пользователя на следующий экран с
`meal_id`, выбранным route и товарами. До сохранения route можно переключить;
после сохранения текущий PoC его не меняет.

Кнопка `Сохранить рецепт` — независимое действие: отправь
`examples/saved_recipe_request.json` в `POST /api/v1/saved-recipes`. Ответ
`created` или `duplicate` считается успехом. При следующем вызове рекомендаций
backend сам добавит этот recipe ID к профилю и сможет вернуть режим `repeat`;
за клик XP не начисляется.

## Шаг 11. Сохранить план, отправить чек и показать прогресс

Для стабильного ready-happy-path используй последовательно
`examples/meal_plan_request.json` и `examples/ready_receipt_event.json`.

Последовательность:

1. отправить `POST /api/v1/meal-plans` и получить статус `created`;
2. отправить `POST /api/v1/events/receipts` с тем же `meal_plan_id`;
3. проверить `status = verified` и `meal_plan.status = completed`;
4. открыть экран кухни;
5. запросить `GET /api/v1/progress/user_meal_demo_001`;
6. показать значения из ответа и позу довольного Домового.

Для cook-happy-path чек должен содержать все `selected_product_ids`. После
`meal_plan.status = collected` приложение вызывает
`POST /api/v1/meal-plans/{plan_id}/complete-cook`; только тогда блюдо и XP
считаются завершёнными.

Ответ на чек уже содержит поле `progress` с полным снимком состояния, поэтому
отдельный GET нужен только для демонстрации того, что состояние действительно
сохранилось на backend. Оба источника дают одинаковую структуру
`ProgressSnapshot`: `avatar_xp`, `avatar_level`, `xp_to_next_level`,
`meals_completed`, `recipes_completed`, `ready_meals_completed`,
`markdown_savings`, `rescue_items`, `purchase_days` и `private_rank` с полями
`position`, `cohort_size`, `percentile`.
Поле `private_rank.cohort` нужно показывать понятной подписью либо не показывать:
оно гарантирует, что cooking households не сравниваются с ready-heavy.

Возможные значения `status`: `verified`, `duplicate`, `pending_review`,
`rejected`. Для демо нужен только первый, остальные пригодятся на экране
ошибки.

## Шаг 12. Добавить понятные состояния интерфейса

Для каждого сетевого экрана нужны всего четыре состояния:

- загрузка;
- успешный ответ;
- понятная ошибка;
- кнопка повторной попытки.

Для защиты этого достаточно. Не делай offline-mode, сложный кэш и глобальную
систему уведомлений.

## Шаг 13. Подготовить приложение к повторному показу

Backend хранит данные в памяти. После отправки одного и того же чека повторный
запрос вернёт статус `duplicate` — это правильное поведение антифрода, а не
ошибка.

Перед новой полной репетицией:

1. останови Uvicorn сочетанием `Control + C`;
2. снова запусти его командой с `--host 0.0.0.0`;
3. перезапусти сценарий с первого экрана.

Во время самой демонстрации backend перезапускать не нужно.

## Шаг 14. Проверить всё на iPhone

Финальный чек-лист:

- `/health` открывается в Safari на iPhone;
- Expo Go видит проект;
- meal-рекомендации приходят именно с backend;
- открывается карточка блюда и виден рекомендованный route с объяснением;
- если оба route доступны, переключатель меняет рецепт на готовое блюдо;
- для cook видны уценка, обычная цена и предупреждение об отсутствии брони;
- план действительно сохраняется через API;
- подтверждение чека обновляет XP и статистику;
- кнопка `Начать заново` возвращает на первый экран;
- текст не выходит за границы на реальном устройстве;
- Mac не уходит в сон во время демонстрации.

## Шаг 15. Сделать резервный вариант

Перед защитой запиши на iPhone видео полного сценария длительностью 30–60
секунд. Оно пригодится, если площадка изолирует устройства в Wi-Fi или Expo Go
не сможет подключиться к Mac.

Для живого показа лучше заранее создать собственную сеть: включить точку доступа
на iPhone, подключить к ней Mac, заново узнать IP Mac и проверить `/health`.

## Что сознательно не делать в демо

- не собирать приложение через Xcode и TestFlight;
- не добавлять регистрацию и авторизацию;
- не подключать PostgreSQL;
- не делать настоящий checkout доставки;
- не реализовывать все ошибки и редкие состояния;
- не добавлять Redux только ради четырёх экранов;
- не выдавать mock recommender за обученную модель.

Если ML-adapter уже готов, backend можно запустить отдельно с
`RECOMMENDATION_ENGINE=model`. Для стабильного первого демо лучше сначала
проверить весь маршрут на стандартном mock, а модель подключить после того, как
четыре экрана работают без ошибок.

## Известные ограничения backend для frontend

- **CORS настроен только на `http://localhost:3000` и `http://localhost:5173`.**
  Для Expo Go на устройстве это неважно: нативный `fetch` в React Native не
  проверяет CORS. Но веб-версия Expo в браузере получит блокировку — если она
  понадобится, нужно добавить origin в `app/main.py`.
- Состояние процессное: рестарт Uvicorn обнуляет прогресс и историю чеков.
- `fulfillment_options` и `available_routes` приходят массивами без гарантии
  порядка.
- Ready-example использует `user_meal_demo_001`; старые recipe/referral examples
  используют `user_demo_001`.
