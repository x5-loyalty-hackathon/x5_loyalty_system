## S1. Известный исключённый компонент составного продукта не проверяется

**Приоритет: исправить до показа исключений на расширенном каталоге.**
Нарушается уже заявленное исключение ингредиентов/категорий; дополнительных
медицинских или аллергологических гарантий для воспроизведения не требуется.

Рецепт требует кабачок и томат. Пользователь исключил `milk`. Единственный
SKU для кабачка — «Кабачки со сливками», в его `ingredient_ids` явно записаны
`["zucchini", "milk"]`. Оба товара доступны и находятся в одном магазине.

**Ожидается:** такой SKU не используется; cook отсутствует, допустимый ready
сохраняется. **Фактически:** HTTP 200, оба маршрута, составной SKU в cook,
`safety_status="approved"`, предупреждений нет.

Причина в [`app/safety.py`](../../app/safety.py): строки 38–44 проверяют ID
требуемого ингредиента, но не все ID фактического продукта. Общая проверка
категории на строке 80 не учитывает `contained_categories` сырого/составного SKU.
Тот же обход воспроизводится при `excluded_categories=["dairy"]` и явно
записанной категории dairy внутри продукта.

Ещё один путь — тот же составной продукт уже в текущем чеке. В
[`app/service.py`](../../app/service.py) на строке 788 его компоненты превращаются
в множество доступных ингредиентов. Связь кабачка с молоком в той же упаковке
теряется; на строках 542–546 покупка считается покрывающей ингредиент.
Cook снова одобрен при исключении молока, хотя состав покупки известен.

Воспроизведения: `excluded_known_raw_component`, `excluded_known_raw_category`,
`excluded_known_receipt_component` в `directed.json` и audit-скрипте.

Минимальный принцип исправления: применять исключения к **фактической позиции,
которую предлагается использовать**, включая все известные компоненты и
категории. При извлечении домашнего ингредиента из чека не терять эту связь.
Для PoC достаточно явной политики и небольших статических составов; новый
онлайн-сервис продуктов для этого не нужен.

## S2. Неизвестный состав ready трактуется как подходящий при исключениях

**Приоритет: определить политику неизвестного состава до подключения
расширенных ready-данных.** Для текущих fixtures с заполненными составами
это не означает, что все показываемые готовые блюда ошибочны.

Пользователь исключил `tomato`. Готовое «Рагу из кабачков и томатов» имеет
подходящий meal intent, `contained_categories=["vegetable"]`, но
`ingredient_ids=[]`: состав не сопоставлен со справочником.

**Ожидается:** отсутствие состава не подтверждает соблюдение исключения.
**Фактически:** cook правильно удалён, остаётся ready-only с
`safety_status="approved"` и пустыми предупреждениями.

[`app/contracts.py`](../../app/contracts.py), строки 194 и 222–225: пустые ID
ингредиентов разрешены, готовой еде достаточно meal intent и категорий.
[`app/safety.py`](../../app/safety.py), строка 67: пересечение пустого множества
с исключениями пусто, поэтому товар проходит. Контракт не различает полный
подтверждённый состав, неполное сопоставление и предполагаемый состав.

Воспроизведение: `unknown_ready_composition_with_hard_exclusion`.
Контроль без пользовательских исключений отдельно проверен и проходит:
аудит не требует запрещать вообще всю еду с неизвестными полями.

Минимальный принцип исправления: статически хранить полноту/источник состава
и определить поведение при жёстком исключении — скрыть неподтверждённый вариант
либо явно отделить его от совместимых рекомендаций. Одна подпись «состав
предполагаемый» при сохранении гарантии совместимости проблему не решает.
Состав food.ru можно использовать для PoC-аналогов, но он не подтверждает
отсутствие компонента в конкретном товаре X5.

## S3. Рекомендована «полная» корзина, которую нельзя выбрать

**Приоритет: значимый дефект сценария, с безопасным отказом ниже по цепочке.**

В рецепте два обязательных ингредиента. В магазине остался один SKU:
либо без `ingredient_ids` в той же категории vegetable, либо составной SKU
с обоими ID. Оба ингредиента получают одну и ту же позицию в `product_options`;
store option объявлен `complete=true`, cook одобрен.

Сохранение единственной возможной корзины через HTTP даёт
`status="rejected", reason_codes=["meal_offer_selection_mismatch"]`.
Мобильная сборка корзины останавливается ещё раньше с текстом:
«Один товар покрывает несколько ингредиентов: количество требует уточнения».
Покупка не создаётся и XP не начисляются — существующие поздние guards полезны.
Ошибка в том, что рекомендация уже обещала выполнимый сценарий.

Причины: fallback по одной категории в [`app/safety.py`](../../app/safety.py):101;
независимый подсчёт покрытия ингредиентов в
[`app/service.py`](../../app/service.py):686. Уникальность выбранных SKU
проверяется только позже: [`app/meal_offer.py`](../../app/meal_offer.py):54 и
[`mobile/src/domain/mealFlow.ts`](../../mobile/src/domain/mealFlow.ts):70.
Fallback по категории также не доказывает идентичность конкретного ингредиента.

Воспроизведения: `empty_mapping_false_complete_basket`,
`same_sku_for_two_ingredients_false_complete_basket`; артефакт включает и ответ
рекомендаций, и последующий отклонённый запрос сохранения плана.

Минимальный принцип исправления: до показа cook проверять существование корзины,
допустимой по текущим правилам сохранения. Для PoC можно ограничить mock-каталог
явным соответствием одного закупаемого SKU одному ингредиенту. Пересчёт
граммовок, остатков упаковок и сложный оптимизатор для устранения этого разрыва
не обязательны.

## Граница X5 и допустимые ограничения PoC

В текущем serving нет прямого чтения офлайн food.ru. `recsys/ready_food_pairs.py`
и `ReadyMealOption` относятся к исследовательскому пути; пользовательский API
собирает ready из переданного `InventoryProduct`. Поэтому рост до 301 пары
сам по себе не добавил 301 готовое блюдо в мобильную выдачу и не создал
подтверждённый состав.

Статические каталоги, фиксированное demo-время, доверенный синтетический чек,
in-memory состояние, отсутствие своего checkout/payment/auth приемлемы для
этого показа. Отдельная система доставки, клинические диеты, точное КБЖУ,
масштабирование и промышленный anti-fraud не нужны, чтобы проверить концепцию.
Покупка дома не доказывает свежесть/остаток продукта; UI уже просит проверить
его наличие. Точные порции и граммовки этим аудитом не подтверждались:
в исходном UI была такая оговорка, в `f5c4795` её убрали вместе с техническими
пояснениями. На демонстрации инструкции следует представлять как PoC-контент;
готовность конкретных рецептов для реального приготовления требует отдельной
редакторской проверки, а не улучшения ML-score.

Новый профиль «Опытный игрок» не получает XP из клиентских полей. Seed проводит
50 синтетических планов и чеков через обычный API, получая 1000 XP; повтор не
добавляет наград. До seed или после сброса памяти профиль имеет нулевой прогресс,
хотя его статическое описание говорит об открытой косметике. Для показа этого
профиля предварительный seed — условие сценария; запуск на живом demo-сервере
в данном аудите не выполнялся.

Для реального встраивания нужны три согласования с владельцами X5, без
дублирования платформенных сервисов:

1. **Каталог → наш модуль:** идентичность SKU и магазина, подтверждённые и
   неизвестные атрибуты состава, свежий снимок цены/остатка/получения. Финальное
   подтверждение цены и наличия остаётся у checkout X5. Наш модуль сохраняет
   источник данных и корректно применяет ограничения; исправления S1–S3 — здесь.
2. **Checkout → игровой факт покупки:** `purchased` должен означать согласованное
   подтверждённое событие, а не закрытие окна или создание неоплаченного заказа.
   X5 отвечает за идентичность и подлинность события; наш модуль — за привязку
   к offer/плану/SKU и идемпотентность. Нужны правила для замен SKU, частичного
   исполнения, отмены уже подтверждённого заказа и возврата: сейчас отзыва наград
   по возврату нет. После ошибки host план остаётся неизменным для retry;
   для изменения корзины host должен завершить попытку отменой или согласовать
   отдельный переход, а не просто повторять постоянную ошибку наличия.
3. **Сессия/данные:** привязать opaque user ID к сессии X5, ограничить доступ
   к progress/book/plans/metrics и передавать только нужную историю покупок.
   Сейчас поля user_id, время, `verified`/`safety_eligible` приходят из доверенной
   фикстуры. Это не авторизация реального клиента. CORS не заменяет эту границу.

Нет оснований заявлять измеренный uplift, точность anti-fraud или качество
матчинга по результатам safety-тестов. Метрики API сами отмечают отсутствие
рандомизированного назначения, реальных UI-показов, расходов и возвратов;
это достаточная честность для описательного PoC-дашборда.

## Воспроизведение и артефакты

[Направленный HTTP-набор](../../scripts/poc_system_safety_audit.py) сохраняет
ожидаемые/фактические маршруты, полный синтетический запрос и ответ для каждого
нарушения. Он намеренно сохраняет красные случаи и не исправляет приложение.
Exit 0 означает завершённую генерацию отчёта; наличие дефектов смотреть в
`failures_by_case`, а не определять по exit code.

```sh
.venv/bin/python -m scripts.poc_system_safety_audit \
  --output artifacts/safety-audit-2026-09-07/directed.json
.venv/bin/python -m pytest -o addopts='' -q --tb=short
.venv/bin/python -m scripts.safety_demo --json
```

Из `mobile/` с доступным Node 24: `npm test`, `npm run test:api`,
`X5_TEST_ENGINE=model npm run test:api`.

[Браузерный скрипт](../../scripts/poc_safety_browser.mjs) использует Playwright
из уже установленного локального окружения, без добавления зависимости проекта.
Сначала из `mobile/` собрать отдельный export:

```sh
EXPO_NO_TELEMETRY=1 EXPO_OFFLINE=1 \
EXPO_PUBLIC_API_BASE_URL=http://poc-audit.test \
npm exec -- expo export --platform web \
  --output-dir ../artifacts/safety-audit-2026-09-07/web
```

Затем из корня: `node scripts/poc_safety_browser.mjs`. При внешней установке
Playwright задать `X5_AUDIT_PLAYWRIGHT_MODULE` как file URL его `index.mjs` и
`PLAYWRIGHT_BROWSERS_PATH` как путь к установленным браузерам. Скрипт сам
запускает изолированный backend с model; все запросы страницы перехвачены,
кроме разрешённого тестового origin сетевые запросы блокируются.

Артефакты текущего запуска находятся в игнорируемом Git каталоге
[`artifacts/safety-audit-2026-09-07/`](../../artifacts/safety-audit-2026-09-07/):
`manifest-start.json`, `manifest-mobile-recheck-start.json`, `manifest-end.json`,
`pytest.xml`, логи backend/mobile (повторные с суффиксом `-final`),
`directed.json`, `safety-demo.json`, `faults-and-provenance.json`,
`static-boundary.json`, `browser.json` с HTTP-трассой и PNG состояний.
Исходники воспроизведений и этот отчёт находятся вне игнорируемых артефактов.
