# Продуктовый материал 2. Критерии успеха, допущения, риски и план проверки

- **Статус:** промежуточная версия, 03.09.2026. Пороги предварительные.

## 1. Предварительные критерии успеха

| Уровень | Метрика | Предварительный критерий |
|---|---|---|
| Case primary | `Δ уникальных дней покупок / пользователя`, `ΔP(дней ≥ N)` на 30/60 днях | статистически значимый рост в тесте против контроля |
| Business guardrail | `Δ contribution margin / eligible user` | не ниже контроля после каннибализации и издержек |
| Персонализация | hit rate; blind `own-history vs shuffled-history` | ≥ 70% на 30–50 профилях (требование кейса) |
| Rescue | incremental value уценённых позиций против текущего baseline | положительный при явно указанном контрфакте |
| Воронка рецептов | impression → open → save → list → purchase → repeat | воспроизводимая, объясняет механизм |
| Доступность | store markdown availability; matched offers/user/30d | порог выбирается после симуляции |
| Антифрод | precision важнее recall; порог блокировки объясним | спорное → review, не автоблок |
| Trust/safety | opt-out, unavailable rate, жалобы, небезопасные предложения | guardrail / kill-критерий |

Частота считается по **уникальным дням**, а не по числу чеков — чтобы рост не
объяснялся дроблением чека или визитом сегодня вместо завтра.

## 2. Ключевые допущения

1. Пользователь готов воспринимать чек как вход в сценарий «что приготовить».
2. Доступной уценки в радиусе достаточно, чтобы rescue-опция появлялась
   регулярно, а не в единичных днях.
3. Проверенного каталога рецептов хватает для персонализации без LLM-генерации.
4. Один дополнительный день покупки экономически оправдывает стоимость показа,
   поддержки и фрод-потерь.
5. Baseline уценённого товара не равен нулю: он мог продаться сам, уйти в
   foodsharing или в списание. Мы вычитаем этот baseline, а не считаем всю
   выручку инкрементальной.
6. Маржа отдельных ингредиентов и маржа всей корзины не складываются, если это
   один и тот же эффект.

## 3. Риски и что с ними делаем

| Риск | Последствие | Митигация в PoC |
|---|---|---|
| Уценка заканчивается до покупки (нет брони) | обманутое ожидание | availability показывается как best-effort, явное предупреждение, обновление перед оформлением |
| Full-price fallback вытесняет rescue | «rescue» становится обычной витриной | доля fallback `markdown → full-price → unavailable` измеряется отдельно |
| Сортировка по missing count побеждает релевантность | нерелевантный рецепт наверху | сначала relevance/safety threshold, только потом missing count |
| Доставка заменяет визит, а не добавляет день | канальный сдвиг вместо uplift | channel shift считается отдельно и не объявляется новым occasion |
| Список читается как скрытый cross-sell | падение доверия | только ингредиенты выбранного рецепта, никакого out-of-recipe |
| Небезопасный short-life SKU в рекомендации | безопасность и жалобы | детерминированный safety-гейт после модели; модель его не отменяет |
| Фрод: дубли чеков, self-referral, связанные аккаунты | ложный прогресс и потери | идемпотентность, схлопывание дня, precision-first review |
| Модель делает чувствительные выводы из чека | приватность | никакого health/family/lifestyle inference; ограничения задаёт пользователь явно |
| Домовой растит только app-retention | нет бизнес-эффекта | game-метрики помечены как диагностика, а не как uplift |

### Специфичные риски AI-решения

- рекомендация не обязана быть верной: любой кандидат проходит детерминированные
  safety- и availability-гейты после ранжирования;
- модель не назначает персональную цену и не участвует в денежных начислениях;
- коммерческие сигналы (supplier payment, ad bid, margin boost) не входят в
  organic rank;
- инструкции по хранению и приготовлению берутся из проверенного каталога, а не
  генерируются;
- пороги антифрода сейчас — объяснимые demo-константы, не обученные на
  размеченных данных.

## 4. Kill / simplify критерии

- own-history relevance не достигает 70%;
- пользователи воспринимают рецепт-список как скрытый cross-sell;
- markdown availability слишком мала и rescue вырождается в full-price витрину;
- рецепты растят размер корзины, но не частоту → модуль становится вторичным;
- Домовой растит только игровые метрики;
- эффект исчезает на 30/60 днях или объясняется дроблением чеков;
- contribution/user ниже контроля после каннибализации и издержек.

## 5. План проверки гипотезы до финала

| Шаг | Что проверяем | Owner | Срок |
|---|---|---|---|
| Evaluation на 30–50 синтетических профилях | hit rate, own vs shuffled ≥70%, coverage, diversity | ML/Recsys | 06.09 |
| Contract test модельного adapter | модель и mock дают одинаково валидный ответ | ML + Backend | 04–05.09 |
| Safety/availability тесты | expired/unsafe/out-of-radius/exclusions не проходят | Backend | сделано (23 теста) |
| End-to-end fixture | recommendation → чек → прогресс → квалифицированный реферал | Backend | 05.09 |
| Симуляция 1–10k профилей | воронка, `Δ purchase days`, `P(≥N)`, contribution/user, sensitivity | ML/Recsys | 06.09 |
| Экономическая проверка | rescue value не смешивается с whole-basket contribution | ML + Product | 06.09 |
| План пилота | дизайн 30/60 дней, arms `C0→C1→C2→C3`, guardrails | Product | 06.09 |

Дизайн эксперимента для пилота: `C0` текущий опыт → `C1` рецепты после чека →
`C2` + список ингредиентов с markdown/full-price → `C3` + Домовой и личный
прогресс. Это отделяет полезность рецепта от commerce-слоя и от игрового слоя.

**Что синтетическая симуляция не доказывает:** причинный uplift. Она проверяет
внутреннюю согласованность механики и экономики. Причинность проверяет только
реальный пилот с тестовой и контрольной группами.
