# ADR-004: книга рецептов и одна точка сбора

- **Статус:** accepted для PoC
- **Дата:** 2026-09-04
- **Основание:** ответы команды на Q5–Q9 и последующий integration review
- **Владелец реализации:** Backend/Integration/Safety

## Контекст

`repeat` раньше зависел только от `user.saved_recipe_ids`, но API не давал
пользователю сохранить рецепт. Одновременно варианты товаров возвращались
отдельно по ингредиентам и могли незаметно собрать одну корзину из нескольких
магазинов. Такой контракт проходил smoke, но не замыкал пользовательский цикл.

Радиус `3 км` также непригоден как дефолт пешего сценария. При этом нельзя
предполагать, что пользователь всегда покупает только у дома: точкой старта
может быть работа, текущая позиция или другое сохранённое место.

## Решение

### Сохранение и `repeat`

- `POST /api/v1/saved-recipes` идемпотентно сохраняет `recipe_id` пользователя;
- `GET /api/v1/saved-recipes/{user_id}` возвращает его книгу рецептов;
- сохранение не начисляет XP и не означает приготовление или покупку;
- при следующей рекомендации backend объединяет книгу с legacy-полем
  `user.saved_recipe_ids`, поэтому сохранённый рецепт доступен в `repeat` даже
  без ручного копирования состояния frontend-ом;
- хранилище остаётся process-local ограничением PoC.

### Контекст покупки

Новый `shopping_context` содержит:

- `anchor_type`: `current_location`, `home`, `work` или `custom`;
- необязательный непрозрачный `anchor_id`, но не адрес и не координаты;
- пеший `radius_km`, по умолчанию `0.75`;
- необязательный `selected_store_id` для явного выбора пользователя;
- `preferred_store_ids`, привязанные именно к выбранному месту.

`InventoryProduct.distance_km` считается источником данных относительно
выбранной точки до вызова API. Backend не выводит дом или работу из истории и
не просит точный адрес.

### Одна точка для cook-корзины

1. Safety сначала удаляет просроченные, небезопасные, отсутствующие и слишком
   далёкие SKU.
2. Магазины сравниваются по числу покрытых обязательных недостающих
   ингредиентов.
3. При одинаковом покрытии сильное предпочтение магазина для выбранной точки
   идёт раньше расстояния; дальше выбирается ближайший и затем стабильный
   `store_id`.
4. Явный `selected_store_id` имеет приоритет над автоматическим выбором.
5. В итоговом cook-варианте все `product_options` относятся только к одной
   выбранной точке. Если она не покрывает все обязательные ингредиенты,
   cook-вариант не возвращается и backend не склеивает несколько магазинов.
6. Ответ содержит краткие `store_selection.options`: UI может показать
   альтернативы, но вариант `complete=false` нельзя выдавать как готовую
   корзину.

Для `ready` одна позиция уже является целым блюдом. Без явного магазина API
может показать готовые варианты из разных достижимых точек; после ручного
выбора магазина фильтрует их по `selected_store_id`.

## Личная позиция

`private_rank` считается отдельно для `cooking_households` и `ready_heavy`.
Выбор route в одном заказе не меняет сегмент: в production его должен задавать
доверенный segmentation job. В PoC он передаётся только как синтетический
`rank_cohort` события чека. Публичного списка пользователей по-прежнему нет.

## Демонстрационные константы

**Прежний вариант, история API 1.2:** `10 XP` за новый день покупки, `20 XP` за
завершённое блюдо, `20 XP` каждому участнику успешного referral и `50 XP` на
уровень. Денежная стоимость referral-награды равна нулю.

**Целевая политика с 06.09 — [ADR-005](005-game-tasks-and-xp.md):** обычный чек
без задания даёт 0 XP; 20 XP выдаются за выбранное выполненное задание с
подходящей подтверждённой покупкой, максимум один бонус на покупочный день.
20 XP за referral и 50 XP на уровень сохранены. Реализовано в API 1.3;
сохранение рецепта по-прежнему не даёт XP.

## Не решает

- production-профиль сохранённых мест и синхронизацию между устройствами;
- получение координат, матрицу реального времени пути и ассортимент X5;
- reservation, оплату и фактическую сборку;
- автоматическое определение rank cohort;
- causal uplift и параметры реального пилота.

Последний пункт фиксируется отдельно в одностраничном плане пилота, а не
выводится из работы API.
