# Пакет конечной meal-выдачи для оценки

Статус: самостоятельный инструмент экспорта конечной выдачи для оценки.
**Не финальный eval и не доказательство ≥70% релевантности.** Методику и оценки
нужно согласовать с ML-участником; этот экспорт не заменяет его исследования.
Для передачи в уже запущенный LLM-прогон — [короткая инструкция](llm-eval-handoff.md).

## Запуск

Из корня репозитория, в новом процессе:

```bash
.venv/bin/python -m scripts.serving_review_pack --profiles 40 --seed 606 --output artifacts/serving-review-40
```

Каталог результата должен быть новым: инструмент откажется перезаписывать
существующий пакет, чтобы не затереть оценки эксперта. Следующий прогон сохранять
под другим именем. Зависимостей сверх dev-окружения проекта нет.

CLI включает настоящий `model`, обращается к `/health` и `/api/v1/meal-recommendations`
через FastAPI TestClient и останавливается при fallback или несовместимом API.
Работающий отдельно demo-сервер не затрагивается: никакого сброса удалённого
состояния, внешней сети, чековых событий и наград.

Файлы результата:

- `llm_inputs.jsonl`: одна строка = профиль с историей и конечная выдача.
  Готовый вход для LLM; нет метки типажа генератора, model_score, вердикта safety,
  флага verified у рецепта и верхнеуровневых reason_codes. Полный каталог и
  остатки вне предложенных вариантов не передаются; рецепты показанных блюд
  и сохранённой книги оставлены. Это проекция для оценки, не запрос к API.
- `manifest.json`: происхождение пакета, контрольные суммы и диагностические
  количества. Это данные для отчёта, не подсказка LLM.
- `responses.json`: полные synthetic-запросы и конечные ответы после safety,
  сборки в одной точке и выбора стратегии; включая пустые ответы и объяснения.
- `review.csv`: по строке на показанное блюдо; пустая выдача тоже оставляет
  строку `empty_response`. Поля reviewer, criterion_version, relevance_label,
  comment оставлены пустыми. Программа не подставляет оценку модели.
- `README.md`: назначение пакета и ограничения.

Флаг `--handoff-only` сохраняет все эти файлы, кроме большого `responses.json`.
Для диагностики сборки корзин нужен полный экспорт без этого флага.

В manifest — seed, число профилей, версия API/движка, хеши каталогов и полных
кейсов, HEAD и дополнительные хеши ключевых исходников (HEAD недостаточен при
незакоммиченном коде). Это не полный реестр всех зависимостей среды.

## Что именно проверяем

Используются существующие `generate_population` и `generate_inventory` с
прежними синтетическими правилами и четырьмя cooking-типажами; новые labels
или поведенческие вероятности не вводятся. ID отделены от обучающей выборки.
Для запроса используется согласованный home-контекст с пешим радиусом 750 м;
прошлая история не объявляется точным запасом дома.

Каталог — текущие **47 serving-рецептов**, а не новый training baseline:
37 обучающих остаются отдельно. Это также не оценка трёх фиксированных
мобильных рецептов. Фактический размер и хеши записываются в manifest.
Число профилей CLI — от 30 до 50; по умолчанию 40. Выборка не отбраковывается
и не пересоздаётся ради непустой или красивой выдачи.

Обязательные границы:

- Генератор остатков содержит сырые ингредиенты, не готовые блюда. Этот пакет
  **не закрывает качество ready-вариантов** и не смешивает ready-heavy с cooking.
- Измеряются только диагностические количества: профили с/без результата,
  число показанных блюд и распределение сгенерированных типажей. Это не hit rate.
- Архетип — служебная метка генератора, не передаётся модели как подсказка.
  Сам по себе он не является независимой экспертной оценкой.
- Непредсказуемые `offer_id` заменены на `null` только в архиве для воспроизводимости.
  Реальный HTTP-ответ обязан содержать token; архив не позволяет активировать
  задания. Остальной смысл и порядок выдачи сохраняются.
- Книга в экспортирующем процессе изначально пуста; сохранённые рецепты из
  синтетического профиля приходят в запросе. Это контекст для рекомендаций,
  не тест сохранения/повтора пользовательской книги.
- Нет сравнения с baseline, экспертных оценок, запусков LLM и расчёта uplift.
  Сначала согласуем критерий и сравнение, потом считаем итоговую метрику.

Тесты: `.venv/bin/python -m pytest tests/test_serving_review_pack.py`.
Они проверяют реальную meal-выдачу на модели, воспроизводимость без случайных
токенов, сохранение пустых строк, отсутствие автоматических оценок/наград,
запрет fallback и перезаписи предыдущего результата.
