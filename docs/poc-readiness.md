## Уже работает

- Вход перед сборкой доставки или после недавней покупки → подбор блюда с
  объяснением → `cook/ready` → товары/уценка одной точки → план → чек → прогресс.
- Сохранение рецепта и следующий `repeat`; готовка подтверждается отдельно от
  покупки, а готовое блюдо завершается чеком. Повтор запроса не удваивает XP.
- Новая кухня, панель и шаги готовки; ошибки не маскируются локальным успехом.
- ML scorer подключён: 37 baseline-рецептов для обучения, 47 в общем каталоге,
  16 признаков (сигнал инвентаря выключен в score по умолчанию); мобильный
  в опубликованной базе был один фиксированный профиль. Локально C2 добавляет
  три переключаемых cooking-профиля с четырьмя прошлыми чеками каждый;
  каталог mobile остаётся из трёх проверенных блюд.
- Backend рефералов, личной позиции и антифрода реализован и покрыт тестами.
- Симуляция/экономика исполняются; одностраничный план пилота есть в draft.

Результаты проверок и карта кода: [integration-handoff.md](integration-handoff.md).
Наличие работающего кода не означает доказанное качество рекомендаций или uplift.

Уточнения к приёмке:

- **P3:** текущий `recsys/evaluation.py::run_evaluation` берёт
  `engine.rank(...)[:top_k]`, не конечный ответ `RecommendationService`.
  Его rule-based оценщик связан с генератором синтетических предпочтений.
  Это существующий диагностический тест, не готовое независимое доказательство
  качества всего продукта. Новую методику/отчёт готовим явно, старые числа не переименовываем.
- **P4:** `recsys/simulation.py` моделирует воронку по заданным вероятностям,
  не проигрывает рекомендации каждому из 10 тыс. покупателей. В базе дополнительный
  покупочный день не предполагается. Рост открытий, смена канала и докупка в уже
  запланированный день не доказывают рост частоты. Нулевая денежная награда не
  обнуляет издержки работы механики.
- **P5:** неоднозначный общий device/payment → проверка, не автоматическое
  обвинение. Пороги — объяснимые demo-правила; численный precision на реальных
  данных не заявляем. Личная позиция не требует публичного списка покупателей.
- **P6:** [pilot-plan.md](pilot-plan.md) уже содержит test/control, покупочные
  дни и маржинальное ограничение. Нельзя выдумать размер выборки/MDE без данных X5;
  такие параметры остаются явно обозначенными условиями запуска реального пилота.

## Усиление игровой концепции — отдельно от обязательной сдачи

- [x] **K1: подтверждённая покупка → продукт появляется на кухне.** Реализовано
  при объединении с актуальным main: начальный чек плюс принятые API покупки,
  без повторного добавления от retry и без ложного успеха при ошибке/отклонении.
  Ready остаётся готовым блюдом; после готовки целые упаковки не списываются.
  Автотесты проходят, внешний вид ещё требует ручной проверки P1.
- [ ] **K2: «закончилось».** Полезная поправка пользователя к предположению о
  наличии дома; полноценный склад, сроки годности из истории и автоматическое
  списание целых упаковок после готовки не требуются.

Декор/сложное развитие дома не расширяем до закрытия основного показа и evidence.
Эти улучшения не становятся молча дополнительными критериями кейса.

## Порядок ближайших действий

1. Проверить объединённую версию, слить в main и передать команде ссылку на handoff в main.
2. **P1 → P2**; K1 уже включён в объединение, следующий полезный кандидат — K2.
3. Параллельно **P3/P4**; к защите закрыть **P5/P6**.
4. Последующие изменения делать небольшими коммитами. Новые коммиты соседней
   ветки фиксировать в очереди интеграции, не откладывая каждый push до нового
   полного merge. В `main` — отдельная согласованная интеграция, не автоматический push.

Новая архитектура, production-интеграции, дополнительные модели и полноценный
холодильник не нужны для замыкания PoC. Личные research-файлы не включаем в
публикацию автоматически; актуальные решения и критерии должны читаться здесь
и в ADR без истории чата.
