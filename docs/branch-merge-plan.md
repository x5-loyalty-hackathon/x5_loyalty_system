## 1. Без новых продуктовых решений

«Механически» означает: правила продукта не меняются, но перенос всё равно
проверяем тестами. Это не команда принять целиком входящие версии файлов.

| ID | Что переносим | Границы и проверка |
|---|---|---|
| M1 | Из mobile: карточки продуктов на кухне, счётчик позиций, компонент основных кнопок `PrimaryAction`, стиль завершения готовки | Визуал/расположение — коллеги. Сохраняем обработчики действий, защиту от повторов и смены профиля. Текст входной кнопки — решение R2; удаление выбора места — R1. |
| M2 | Сокращённый блок пояснений кухни из `8de89ea` | Остаётся «Из чеков, не точный остаток дома». Карточки не становятся учётом реально оставшейся еды. Явная demo-подпись в профиле и demo-действия не удаляются; ограничения сохраняются в документации. |
| M3 | ML `bfd35d4`: проверки структуры файла каталога готовой еды и понятные ошибки загрузки | Переносим проверки, сохраняя наши импорты `recsys.experimental` и более строгую проверку соответствия готового блюда рецепту. ### Уже решено — повторного ответа не нужно

- **Не возвращаем XP за обычную покупку.** Награда остаётся за выбранное
  задание, подходящий принятый чек и завершение; действует лимит покупочного дня.
- **Не переносим** `/api/v1/events/recipes/completed` как второй путь выдачи XP.
  Готовку завершает наш meal-plan endpoint, готовое блюдо — подходящий чек.
- **Не удаляем всю упаковку при готовке.** Во входящей серверной кухне
  используется именно такое упрощение; оно не соответствует нашему контракту.
- Исправленный referral-код и ранее перенесённые проверки приглашения/подбора
  повторно не добавляем. Исследовательские выводы не переписывают принятые ADR.
- Три текущих мобильных рецепта и их обязательные ингредиенты сохраняем:
  `pasta_tomatoes` не теряем, у супа остаётся лук, базилик не становится
  обязательным для болоньезе. Сырники из соседнего mock-каталога сами по себе
  не расширяют наш демонстрационный сценарий.
- Согласованный переключатель синтетических покупателей — только внизу профиля.

## 2. Нужны твои ответы

Ниже **три карточки решений**, не новый список требований ко всему PoC.
Рекомендации не считаются ответами. Можно заполнить поля или ответить в чате
по номерам. Если поле пустое, связанную часть кода не меняем.

### R1. Оставляем ли выбор «у дома / у работы / рядом / моё место»?

**Сейчас:** на экране подбора можно выбрать место. В демо выбор действительно
меняет расстояния до магазинов в запросе; настоящая геолокация не используется.
Ранее мы договорились не привязывать человека только к дому.

**У коллеги:** переключатель и пояснение радиуса удалены. Поле места в API
остаётся, но в текущем UI без другого выбора будет использоваться домашняя
точка по умолчанию. Это сокращение доступного сценария, не только уборка текста.

- **A — сохранить текущий выбор на экране подбора** (рекомендую).
  Новые карточки/стиль принимаем, этот фрагмент удаления не принимаем.
- **B — убрать выбор только из показываемого PoC.** Демонстрируем одну
  условную домашнюю точку; поддержку других мест в API сохраняем, но не
  заявляем доступной пользователю через интерфейс.
- Если хочется **перенести** выбор в другое место — напиши конкретно куда;
  расположение нового элемента самостоятельно не выбираем.

**Ответ R1:** а у нас же сейчас концепция по сути сместилась в сторону доставки? (какая нам разница откуда чек и в какой конкретно магазин он пойдёт) Может тогда использовать сохранённые адреса?

### R2. Что должна обещать главная кнопка на кухне?

**Сейчас:** «Подобрать для доставки» запускает сценарий с выбранным способом
получения «доставка». На экране товаров способ можно изменить; реального
заказа в X5 наш PoC не отправляет.

**У коллеги:** подпись стала «Подобрать блюдо», но обработчик остался тем же:
это всё ещё вход с доставкой по умолчанию. Цвет/размер кнопки можно принять
независимо от текста и назначения.

- **A — сохранить «Подобрать для доставки» в новом оформлении** (рекомендую).
  Сохраняется согласованный вход рядом со сценарием доставки.
- **B — принять «Подобрать блюдо»**, сохранив доставку по умолчанию и
  возможность изменить её на экране товаров. Это сознательно более общая
  формулировка, а не новый нейтральный сценарий без выбранного способа получения.

**Ответ R2:** B - иначе очень криво звучит и несёт какой-то смысл только для регулярного пользователя

### R3. Подключаем ли две новые серверные возможности перед ближайшим push?

В ML-ветке вместе со старой готовкой добавлены **две отдельные GET-ручки**.
Их можно адаптировать независимо, не принимая старые начисления и списания.

| Возможность | Что есть сейчас | Что даст перенос и что потребуется |
|---|---|---|
| **Кухня по принятым чекам**, `GET /api/v1/kitchen/{user_id}` | Список в клиенте: текущий demo-чек и покупки этой сессии. После перезапуска клиента список покупок сессии не восстанавливается. | Сервер возвращает позиции из своего журнала принятых чеков; они восстанавливаются при повторном входе, пока жив процесс backend. Нужны адаптация к нашему журналу, подключение mobile и защита смены профиля. Это история покупок, **не точные остатки**, не расход по рецептам и не хранение после перезапуска backend. |
| **Инструкции рецептов**, `GET /api/v1/recipes/{recipe_id}` | Проверенные demo-шаги трёх блюд лежат в `mobile/src/fixtures/recipeDetails.ts`; выдача блюд уже приходит с сервера. | Инструкции тоже приходят с сервера. Нужно выровнять справочник с нашими тремя блюдами, сохранить тексты/состав, обработать загрузку, ошибку и незнакомый рецепт. Это перенос источника контента, **не генерация новых рецептов**. |

Для каждого пункта выбери **«сейчас»** или **«после ближайшего merge»**.
Рекомендация для быстрого сведения: оба после ближайшего merge — действующий
показ не зависит от этих GET. Это предложение о порядке работ, не отказ от
серверной кухни и не признание текущих ограничений окончательным продуктом.
Если выбираем «сейчас», перенос считаем небольшой отдельной реализацией с
тестами, а не простым разрешением Git-конфликтов.

**Ответ R3 — кухня по чекам:** после merge

**Ответ R3 — инструкции рецептов:** после merge

## 3. Порядок исполнения после ответов

1. Обновить refs, проверить чистоту tracked-файлов и зафиксировать точные
   входящие коммиты. Если появились новые изменения, отдельно показать delta;
   ответы на этот план не являются разрешением на ещё неизвестные изменения.
2. Свести `main` в `experiment/vxofi` без изменения содержимого (M5).
3. Перенести совместимые ML-проверки/оговорки (M3–M4) и запустить профильные
   тесты. Не заменять рабочий recommender исследовательской версией.
4. Свести `mobile-polish` с решениями R1–R2. Сохранить согласованный профиль,
   обработчики API 1.3 и визуал коллеги; обновить эталон с явными исключениями.
   Проверки каталога и разбор mobile можно выполнять параллельно в разных файлах.
5. Если выбрано в R3 — адаптировать только соответствующие GET и клиентские
   вызовы. Старый completion не подключать. При необходимости нового видимого
   состояния/кнопки сначала показать конкретное предложение, не менять UI молча.
6. Общая приёмка: полный pytest; client tests; mock и model API-flow;
   TypeScript; экспорт web/iOS/Android; браузерный smoke на узком экране.
   Особое внимание: правильный вход delivery/next_visit, R1, профиль A→B→A,
   cook/ready/repeat, сетевой retry, отсутствие passive XP, лимит дня, метрики.
7. Обновить [памятку](integration-handoff.md): исходные коммиты, что перенесено,
   что адаптировано, что отложено и почему. Опубликовать `experiment/vxofi`.
   Слияние **в main** — отдельный шаг через PR/review, без прямого push в main.
