# ADR-003: Выбор типа персонального челленджа

- Дата: 2026-09-04
- Статус: accepted
- Решение подтверждено: `vxofi`, 2026-09-04
- Межконтурные владельцы реализации: Product/UX, ML/Recsys и Backend
- Версия HTTP-контракта после изменения: `1.1`

## 1. Проблема предыдущего контракта

В версии `1.0` каждый рецепт получал ровно одну метку по приоритетному правилу:

```text
сохранён → repeat
иначе пересекается с текущим чеком → current
иначе → explore
```

Это смешивало две независимые характеристики:

1. знакомство пользователя с рецептом: знакомый или новый;
2. усилие на сбор корзины: продукты уже куплены, есть дома или требуют докупки.

Из-за этого новый для пользователя рецепт с продуктами из сегодняшнего чека
маркировался `current`, а не `explore`. Начальная выдача также могла состоять из
трёх `current`, то есть API не делал явного персонального выбора типа
челленджа. Такая схема плохо закрывала требование кейса «выбор игровой механики
с объяснением».

## 2. Решение

`current / repeat / explore` — это **стратегии персонального челленджа**, а не
взаимоисключающие свойства рецепта:

- `current` — максимально использовать продукты текущего чека;
- `repeat` — вернуться к сохранённому или ранее приготовленному блюду;
- `explore` — попробовать новое для пользователя блюдо, сохраняя соответствие
  его истории, ограничениям и бюджету.

Один рецепт может быть допустим для нескольких стратегий. Например, сохранённый
омлет из продуктов текущего чека подходит и для `current`, и для `repeat`.
Новый рецепт из тех же продуктов подходит и для `current`, и для `explore`.

`missing_count`, источники ингредиентов и стоимость докупки остаются отдельными
признаками. Поэтому `explore` может быть:

- дополнением текущего чека или домашних запасов;
- полной новой корзиной, если ни одного ингредиента ещё нет.

Полная новая корзина имеет больше трения и может восприниматься как реклама.
Она не становится default-челленджем без явного выбора `explore`.
Ready-only вариант требует покупки одного готового блюда и не считается полной
корзиной сырых ингредиентов. Он не наследует `current` от ингредиентов
недоступного cook-рецепта: без явного совпадения доступного ready-SKU с текущим
чеком такой вариант относится только к `repeat` либо `explore`.

## 3. Начальная выдача и явный выбор режима

Если `requested_mode` не передан:

1. модель или smoke-adapter ранжирует рецепты по релевантности;
2. backend применяет safety и availability;
3. безопасные рецепты раскладываются по всем допустимым стратегиям;
4. для каждой стратегии выбирается не более одного представителя;
5. один представитель становится default;
6. остальные возвращаются как альтернативы, только если для них существует
   безопасный уникальный кандидат.

Начальная выдача содержит максимум три блюда и не содержит двух рекомендаций с
одинаковым `mode` или одинаковым `recipe_id`. Квоты «обязательно показать все
три режима» нет: слабая или недоступная альтернатива не используется для
заполнения интерфейса.

Default выбирается детерминированно среди режимов, не требующих opt-in:

```text
меньше missing_count
→ выше model_score
→ стабильный приоритет current, repeat, explore
```

Это demo-policy, а не измеренный production-selector. ML/Recsys owner может
заменить utility и пороги после eval без изменения внешней формы ответа.

Если `requested_mode` передан явно, пользователь уже выбрал стратегию. API
может вернуть до `limit` рецептов одного режима. Поэтому запрет на несколько
одинаковых режимов относится только к начальной выдаче, а не к каталогу внутри
выбранного режима.

## 4. Полная корзина в `explore`

Полной считается корзина, в которой ни один **обязательный** ингредиент
выбранного рецепта не имеет источник `receipt` или `home`. Необязательный
гарнир из чека или домашних запасов сам по себе не превращает новую корзину в
частичную.

- В начальной выдаче backend сначала ищет частичный `explore`, использующий
  уже имеющиеся продукты.
- Если безопасен только full-basket `explore`, он может быть возвращён как
  opt-in альтернатива, но входит в `explicit_choice_required` и не становится
  `default_mode`.
- После запроса `requested_mode=explore` пользовательский выбор считается
  явным, и full-basket вариант может быть показан.
- Лимит стоимости и числа недостающих продуктов для production остаётся
  отдельным продуктовым параметром. В контракт не зашит неподтверждённый
  денежный порог.

## 5. HTTP-контракт `1.1`

`RecommendationResponse` и `MealRecommendationResponse` получили одинаковое
поле:

```json
{
  "challenge_selection": {
    "default_mode": "current",
    "available_modes": ["current", "repeat", "explore"],
    "mode_reason_codes": {
      "current": [
        "current_basket_strategy",
        "selected_by_effort_then_relevance"
      ],
      "repeat": [
        "saved_recipe_strategy"
      ],
      "explore": [
        "novel_recipe_strategy",
        "full_basket_requires_explicit_choice"
      ]
    },
    "explicit_choice_required": ["explore"]
  },
  "recommendations": []
}
```

### Инварианты `ChallengeSelection`

- `default_mode` либо `null`, либо входит в `available_modes`;
- ключи `mode_reason_codes` в точности равны `available_modes`;
- `explicit_choice_required` является подмножеством `available_modes`;
- `default_mode` не может требовать явного выбора;
- первая рекомендация начальной выдачи соответствует `default_mode`, если он
  существует;
- mode и recipe не дублируются в начальной выдаче;
- отсутствие качественной альтернативы не заполняется нерелевантным рецептом.

`available_modes` и `explicit_choice_required` — упорядоченные списки без
дублей, а не JSON-представление set. Default mode идёт первым в начальном
ответе; остальные следуют стабильному приоритету `current, repeat, explore`.

## 6. Три уровня объяснений

Причины намеренно разделены:

| Поле | На какой вопрос отвечает |
|---|---|
| `challenge_selection.mode_reason_codes` | Почему выбран этот тип челленджа? |
| `recommendation.reason_codes` | Почему предложено именно это блюдо? |
| `meal_recommendation.route_reason_codes` | Почему по умолчанию `cook` или `ready`? |

UI не должен соединять все коды в одну длинную фразу. На карточке достаточно
одного объяснения каждого реально показанного решения; остальные коды нужны для
аудита и отладки.

### Текущие challenge-level reason codes

| Код | Технический смысл | Возможный короткий текст UI |
|---|---|---|
| `explicit_mode_request` | пользователь сам выбрал mode через `requested_mode` | «Вы выбрали этот режим» |
| `current_basket_strategy` | стратегия использует хотя бы один ингредиент текущего чека | «Подходит к сегодняшним покупкам» |
| `saved_recipe_strategy` | стратегия строится вокруг сохранённого рецепта | «Можно повторить сохранённое блюдо» |
| `novel_recipe_strategy` | рецепт не находится в `saved_recipe_ids` | «Новое блюдо для вас» |
| `selected_by_effort_then_relevance` | этот mode победил demo-сортировку missing count → score → stable priority | «Меньше докупать, при этом подходит вам» |
| `full_basket_requires_explicit_choice` | у возвращённого explore нет ингредиентов из `receipt/home` | «Для этого блюда нужно собрать новую корзину» |

`alternative_mode_available` не нужен: наличие альтернативы уже полностью
выражено `available_modes`. При явном запросе mode ответ содержит и код
стратегии, и `explicit_mode_request`.

Recipe-level коды вычисляются backend после assembly и safety, поэтому они
описывают фактически возвращённый оффер. Например,
`safe_markdown_option_available` появляется только при наличии прошедшего
фильтр markdown-SKU. Внутренние признаки ML (`personalized_discovery`,
`high_discovery_acceptance`, прогноз доступности уценки и другие) не
передаются пользователю как установленные факты. Реестр публичных кодов и
текстов находится в `app/explanations.py`.
Утверждение о «фактической стоимости докупки» не выдаётся: пока в схеме нет
надёжной нормализации количества рецепта и размера упаковки, такой текст был бы
точнее данных.

Фразы справа не являются финальным UX-copy. Они показывают семантику кода и не
должны использоваться для вывода чувствительных характеристик пользователя.

## 7. Граница с ML/Recsys

Текущий `ModelRecommendation.mode` сохраняется как legacy hint, чтобы не ломать
параллельную разработку smoke-adapter. Внешний mode в API `1.1` назначается
challenge-selector после safety и может отличаться от этого hint.

Это осознанный временный компромисс. Финальный model contract должен либо:

- возвращать recipe relevance независимо от режима, после чего selector
  оценивает стратегии отдельно;
- либо возвращать score по каждой паре `(recipe, mode)`.

Выбор между этими внутренними вариантами принадлежит ML/Recsys owner и не
меняет зафиксированные HTTP-инварианты.

## 8. Известные ограничения текущей реализации

- `repeat` пока определяется только через `saved_recipe_ids`: история реально
  приготовленных, но не сохранённых блюд отсутствует во входном профиле;
- production propensity к discovery ещё не реализована отдельным наблюдаемым
  сигналом;
- backend smoke-контура не задаёт отдельный порог «слабого рецепта»: он
  считает все кандидаты model adapter прошедшими upstream relevance gate;
  определение eligibility/порога принадлежит ML/Recsys eval;
- default demo-selector использует effort/relevance, а не обученную вероятность
  принятия механики;
- cost-cap для full-basket `explore` должен быть согласован отдельно;
- текущие reason codes являются первой версией и требуют отдельной проверки на
  дублирование, полноту и понятность.

## 9. Автоматические проверки

Тесты фиксируют:

- уникальность mode и recipe в начальной выдаче;
- согласованность `default_mode`, `available_modes` и reason codes;
- возможность `explore` использовать текущий чек;
- запрет неявного default для полной новой корзины;
- снятие opt-in ограничения после явного `requested_mode=explore`;
- одинаковый `challenge_selection` у recipe- и meal-level ответов.

## 10. Совместимость `1.0 → 1.1`

| Изменение | Тип | Последствие |
|---|---|---|
| обязательный `challenge_selection` в двух recommendation responses | breaking для строгого клиента `1.0` | frontend должен читать selector до карточек |
| упорядоченные `available_modes` и `explicit_choice_required` | стабилизация JSON | порядок одинаков для одинакового входа |
| `IngredientRecommendation.required` | additive | позволяет корректно отличить full basket от необязательного гарнира |
| новые публичные recipe/route reason codes | semantic breaking | UI использует реестр `app/explanations.py`, внутренние ML-коды не показывает |
| поля meal plan/progress/receipt из ADR-002 | additive к соответствующим ответам | старые клиенты, запрещающие extra fields, должны обновить schema |
| общий `contract_version = 1.1` | осознанный общий bump PoC | sample artifact и оба runtime engine проверяются тестами |
