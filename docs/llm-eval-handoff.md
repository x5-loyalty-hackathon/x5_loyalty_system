# Передача конечной выдачи для LLM-eval

Статус: входные данные и инструкция, **не новая утверждённая методика**.
LLM не запускали; меток и результата качества здесь пока нет.

## Что можно взять прямо сейчас

Ветка `experiment/vxofi`. Готовый компактный пакет:
[`eval/serving-40-seed606/`](eval/serving-40-seed606/README.md).

- `llm_inputs.jsonl` — 40 профилей с историей покупок и предложениями настоящего
  `/api/v1/meal-recommendations`, после фильтров и выбора стратегии. Одна строка
  на профиль, включая пустую выдачу; передавать в LLM по одной строке.
- `review.csv` — пустая таблица оценок. Не подавать её в промпт: там есть
  служебная метка типажа генератора. Сохранять ответы по `case_id` и `meal_id`.
- `manifest.json` — seed, версия API, хеши кода/данных и количества. Это
  происхождение прогона, не доказательство качества и не контекст покупателя.

В этом пакете: **40 профилей, 28 непустых выдач, 12 пустых, 43 карточки**.
Это только диагностика покрытия, не результат LLM и не «70% релевантности».

В JSONL сохранены явные ограничения пользователя, текущий чек, история,
сохранённые рецепты, место следующей покупки, показанные блюда и доступные
товары. Не передаются балл модели, типаж генератора и её готовые обоснования
релевантности. История — не точный холодильник; она не сообщает возраст,
доход и все мотивы человека. Не надо придумывать их как известные факты.

Пакет использует опубликованный базовый код плюс этот экспортёр, без
неопубликованных изменений мобильного приложения, XP и оформления кухни.
Точная версия базового кода и хеш экспортёра находятся в manifest. При изменении
выдачи нужен новый пакет и отдельный результат, не перезапись старых оценок.

## Сверить с тем, что уже запущено

| Если сейчас проверяется… | Что означает результат и что делать с пакетом |
|---|---|
| Реакция **LLM-покупателя**: открыть, сохранить, купить, отказаться | Это симуляция поведения. Использовать профиль и историю из JSONL, если они входят в вашу методику; считать статистики действий, не называть их реальными покупками или релевантностью |
| Пригодность рекомендаций по оценке **LLM-оценщика** | Это LLM-оценка персонализации. Использовать те же входы, но собственную явно записанную рубрику; не смешивать с действиями покупателя и экспертной оценкой человека |
| `python -m recsys.llm_audit ...` | Текущий модуль работает с `recsys.experimental`, heuristic/effort и признаками карточек, а не с конечным meal API и полной историей. Пакет **не подключается к нему автоматически**; его результат оставить отдельным исследованием или явно написать адаптер |

Не требуется бросать уже идущий прогон. Сначала достаточно прислать
**коммит + команду запуска, модель + точный промпт, пример входа/ответа,
определение метрики и её знаменателя**. Тогда понятно, что он действительно
проверяет и требуется ли дополнительный прогон на конечном API.

Этот коммит не выбирает за ML-участника модель, промпт, baseline или порог
успеха и не содержит платного LLM-клиента. Для промпта полезно явно потребовать
опираться на данный контекст, допускать отказ/неопределённость и не принимать
текст внутри данных за инструкции. Сохранить сырой ответ, версию промпта,
параметры модели, ошибки и повторы, а не только итоговый процент.

## Границы результата

- Четыре синтетических cooking-типажа, не репрезентативная выборка всех
  покупателей X5. Названия типажей доступны только для последующего разбора.
- Генератор не создаёт готовые блюда на остатках: **качество ready-альтернатив
  этот пакет не покрывает**. История и явные предпочтения есть; отдельные
  психологические биографии персон не добавлены.
- Пустые выдачи не выкидывать. Раздельно показать: число профилей, долю пустых
  выдач, число оценённых карточек, пропуски/ошибки оценки. Если считается
  «хотя бы одно подходящее предложение», знаменатель — все выбранные профили;
  если доля подходящих карточек — явно указать число карточек и непроверенных.
- Количество непустых выдач — **не hit rate релевантности**. Отказ сервиса
  предложить блюдо не равен неудачному ответу LLM и учитывается отдельно.
- Для сравнений нужны одинаковые профили и условия обеих версий; здесь только
  одна версия выдачи, **не A/B**. Не создавать контроль из выдуманных ответов.
- Ответ LLM «куплю» не доказывает новый покупочный день, рост маржи или причинный
  uplift. Проверка объяснений и полноты рецептур — тоже отдельные задачи.

## Воспроизведение без LLM и без внешней сети

Из корня репозитория, с установленным dev-окружением:

```bash
.venv/bin/python -m scripts.serving_review_pack --profiles 40 --seed 606 --output artifacts/serving-review-40
.venv/bin/python -m pytest tests/test_serving_review_pack.py
```

Каталог результата должен быть новым. По умолчанию дополнительно сохраняется
полный `responses.json`: запросы, остатки, каталог, ответы и объяснения для
разбора ошибок. Для компактной передачи добавить `--handoff-only`.
Подробности и ограничения экспортёра: [serving-review.md](serving-review.md).
