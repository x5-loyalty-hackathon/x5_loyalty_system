# Воспроизводимый показ referral, antifraud и личной позиции

Из корня checkout, в Python-окружении проекта с установленным `.[dev]`:

```bash
python -m scripts.safety_demo
```

Команда запускает настоящие FastAPI HTTP-обработчики через `TestClient` в новом
локальном процессе. Внешний сервер не нужен. Состояние уже запущенного backend
не меняется: у процесса демо собственный пустой `InMemoryStateRepository`,
который исчезает при завершении. Повтор команды даёт тот же результат.
Новые экраны и изменение политики наград для показа не нужны.

Текст показывает реальные `status`, `fraud_score`, `reason_codes`, XP,
покупочные дни и личную позицию из ответов API. Полное доказательство, включая
подготовительные HTTP-запросы и необрезанные ответы, доступно командой
`python -m scripts.safety_demo --json`. Это технический протокол синтетического
сценария; он содержит его тестовые user IDs, а не публичный рейтинг людей.

## Последовательность и ожидаемый смысл

| Событие | Что должно быть видно в API |
|---|---|
| Приглашённый ещё не покупал | `not_qualified`, `invitee_has_no_verified_purchase_day`, награда `0+0` |
| Первый чек приглашённого | `verified`, один покупочный день, **0 XP** без выбранного и выполненного meal-задания |
| Повторная проверка приглашения | `approved`, отдельная однократная referral-награда **20+20 XP**, денежная стоимость 0 |
| Повтор referral и того же чека | `duplicate`, новые XP не начисляются, баланс и счётчики сохранены |
| Self-referral | `rejected`, `self_referral`, score 1, прогресс сохранён |
| Тот же чек отправлен другим пользователем | `rejected`, `receipt_claimed_by_another_user`, score 1, прогресс сохранён |
| Код принадлежит другому приглашающему | `rejected`, `invite_code_does_not_match_inviter`, score 1, награды нет |
| Общий device hash | `pending_review`, `shared_device_hash`, score 0.75, награды нет |
| Общий payment hash / оба совпадения | `pending_review`, соответствующие reason codes, score 0.8, награды нет |
| Чек из будущего | `pending_review`, `receipt_timestamp_in_future`, score 0.8, прогресс сохранён |
| Личная позиция и отдельная когорта | Позиция приглашающего меняется `2/3 → 1/3` при `0 → 20 XP`; участник `ready_heavy` с 40 XP учитывается в своей группе `1/2` |
| Запрос публичной таблицы | `/api/v1/leaderboard` возвращает HTTP 404; `private_rank` содержит только cohort, position, cohort_size, percentile |

Шесть подготовительных HTTP-событий создают сравнение для рейтинга: два
покупателя `cooking_households`, два `ready_heavy` и две успешные referral-награды.
После первой покупки основного приглашённого cooking-группа содержит троих.
Равные XP дают одинаковое место: переход на `1/3` означает разделённое первое
место, а не единственного победителя. Позже отдельный готовый к проверке
приглашённый добавляется в `ready_heavy` для примеров общих device/payment.
Число и выбор профилей — только воспроизводимая техническая фикстура.

Код приглашения создаёт серверный helper
`app.referral_codes.issue_invite_code(inviter_user_id)`; отдельного endpoint
выдачи в этом сценарии нет. Отказы и начисление проверяет обычный API.

## Что этот показ не измеряет

Все пользователи, чеки, временные отметки, хэши и когорты синтетические.
`verified` означает принятие тестового события текущей PoC-политикой; реальная
кассовая интеграция и production-auth здесь не появляются. Наличие приватной
формы ответа не доказывает production-контроль доступа.

`fraud_score` — вес правил, не калиброванная вероятность мошенничества.
**Precision и false-positive rate не измерены:** нет размеченной реальной
выборки. Общий телефон или способ оплаты дают review, а не безусловную
блокировку; ручное решение после review этот сценарий не реализует.
XP и изменение позиции не доказывают интерес к игре, экономический uplift
или оптимальность порогов. Правила покупки и отдельной referral-награды
остаются правилами [ADR-005](decisions/005-game-tasks-and-xp.md).

Проверка: `python -m pytest tests/test_safety_demo.py`. Тесты проходят через
HTTP, проверяют повторяемость после reset тестового repository и подтверждают,
что запуск CLI не меняет состояние другого процесса даже при совпадении IDs.
