# X5 Домовой × recipe-first «Спасённая корзина»

> **Статус:** согласованный командой current state по итогам обсуждения
> 2026-09-03. Это рабочие продуктовые решения для дальнейшей проверки, а не
> доказанные результаты пилота. Название и production-policy ещё могут меняться.

## 1. Что выбрано для PoC

| Вопрос | Текущий рабочий ответ |
|---|---|
| Основной offer | `V3 + V4`: recipe-first корзина с выбором уценённых ингредиентов + мир Домового |
| Точка выдачи | достижимый радиус, не один домашний магазин |
| Исполнение списка | стандартная доставка либо сохранение к следующему визиту |
| Размер набора | не фиксирован; рецепты сортируются по числу недостающих продуктов, меньше — выше |
| Предоплата и бронь | отсутствуют |
| Базовые категории | фрукты, овощи, молочные продукты, мясо и другие short-life staples для базовых блюд |
| Обычные complements | только ингредиенты выбранного рецепта; out-of-recipe рекомендации исключены |
| Первый сегмент | домохозяйства, регулярно покупающие продукты для приготовления блюд |
| Gambling-like механика | не входит в первые четыре экрана |
| Рейтинг | только личная статистика, без public leaderboard |
| Нет уценённого ингредиента | предложить подходящий full-price вариант; если нет и его — убрать недоступный candidate/отменить сборку |
| Доступность | recipe feed доступен ежедневно в приложении; push не ежедневный |
| Дополнительная денежная награда | отсутствует; при проблемах показывается стандартное уведомление в приложении |

## 2. Ключевой pivot: не готовый физический бокс

Предыдущая версия предполагала заранее собранную магазином коробку с точным
составом, бронью и pickup. Текущая версия устроена иначе:

- магазин не собирает и не удерживает отдельный набор;
- пользователь начинает с персонального рецепта;
- внутри рецепта видит, что уже было в чеке и чего не хватает;
- для недостающего может выбрать уценённый товар в достижимом радиусе;
- если уценки нет, доступен full-price товар;
- корзина существует как цифровой recipe plan и становится обычной покупкой на
  кассе.

Поэтому рабочее название «Спасённая корзина» здесь означает **корзину рецепта с
опциональными rescue-позициями**, а не mystery-box и не заранее упакованный лот.

Это снимает сборку, предоплату, no-show и удержание товара под бронь, но создаёт
другой риск: уценённый SKU может закончиться до прихода пользователя. PoC должен
показывать availability как best-effort, а не обещание выдачи.

## 3. Идея в одной фразе

> После покупки recommender превращает чек в персональные идеи блюд, предлагает
> как знакомые, так и новые рецепты, помогает собрать недостающие ингредиенты с
> возможностью выбрать уценку, а следующая покупка продолжает личный мир
> Домового.

```text
подтверждённый чек + история + явные предпочтения
→ персональные рецепты, отсортированные по missing count и relevance
→ знакомый repeat ИЛИ персональное discovery из новых продуктов
→ сохранить/изменить рецепт
→ выбрать для недостающих ингредиентов markdown или full-price SKU в радиусе
→ заказать стандартную доставку ИЛИ сохранить список к следующему визиту
→ новый чек обновляет рецепт, личную статистику и дом Домового
```

## 4. Пользовательский цикл

### Шаг 1. После покупки

После нового чека на обычной поверхности приложения появляется карточка:

> «Из вашей корзины уже можно приготовить два блюда — и открыть одно новое».

При открытии продукты из чека появляются на кухне Домового. Пользователь сразу
получает полезный результат, даже если ничего больше не купит:

- рецепт почти или полностью из текущей корзины;
- знакомый сохранённый рецепт;
- новое персонально подобранное блюдо, которое может потребовать новый набор.

### Шаг 2. Выбор рецепта

Recommender показывает небольшой top и объясняет каждую рекомендацию. Основная
сортировка — по числу недостающих ингредиентов: меньше missing items выше, если
рецепт проходит relevance и safety gates.

Пользователь может:

- выбрать рецепт;
- переключить `из текущей корзины / повторить / попробовать новое`;
- заменить или убрать ингредиент;
- отметить `есть дома`;
- сохранить на потом;
- отказаться без потери истории.

### Шаг 3. Сбор recipe basket

Каждый ингредиент получает одно из состояний:

| Состояние | Что видит пользователь |
|---|---|
| `уже куплено` | товар/категория найдены в текущем или недавнем чеке |
| `есть дома` | пользователь подтвердил вручную |
| `уценка рядом` | подходящий short-life SKU найден в магазине достижимого радиуса |
| `full-price` | обычный подходящий SKU, если уценки нет |
| `нет в наличии` | нет допустимого аналога; candidate исключается или рецепт требует изменения |

Уценка — пользовательский выбор внутри рецепта, а не обязательное условие.
Обычные позиции допускаются только как ингредиенты выбранного блюда. Блоки
«с этим покупают» и другие out-of-recipe cross-sell рекомендации в PoC
отсутствуют.

### Шаг 4. Доставка или следующий визит

Отдельной предоплаты и брони rescue-позиции нет. После сохранения рецепта
пользователь выбирает один из двух путей:

- **доставка:** передать recipe basket в стандартный checkout доставки;
- **следующий визит:** сохранить список и использовать его при обычном походе в
  один из магазинов радиуса.

Стандартная оплата заказа доставки не считается «предоплатой за rescue-бокс».
Для PoC достаточно симулировать передачу списка и успешный/частичный результат;
production-интеграция с каталогом, checkout и доставкой остаётся вне scope.

Перед оформлением/походом система обновляет best-effort availability. Для
следующего визита она явно предупреждает, что уценённый товар не зарезервирован.
Для доставки действуют стандартные подтверждение наличия, замена и отмена.

Если уценённый SKU закончился:

1. показать совместимый full-price вариант;
2. разрешить заменить ингредиент или рецепт;
3. если подходящего товара нет — убрать недоступный candidate/отменить сборку;
4. не выдавать денежную компенсацию; показать стандартное уведомление.

### Шаг 5. Новый чек и мир

После следующего подтверждённого чека:

- найденные ингредиенты переходят из `missing` в `purchased`;
- Домовой получает продукты и новую сцену/объект;
- рецепт остаётся в личной книге вместе с заменами;
- личная статистика обновляется;
- пользователь сам подтверждает приготовление: покупка ингредиентов не
  доказывает, что блюдо приготовили.

## 5. Почему пользователь зайдёт

Вход строится на двух типах ценности:

1. **После чека:** любопытство и немедленная utility — во что можно превратить
   конкретную покупку.
2. **Между покупками:** ежедневный recipe feed с новыми персональными идеями и
   видимыми вариантами экономии рядом, которые можно отправить в доставку или
   сохранить к следующему визиту.

Приложение может быть открыто каждый день, но ежедневный push запрещён как
default. Push отправляется только по отдельной policy: высокая релевантность,
реальная доступность, подходящий cadence и frequency cap.

Если нет уценки, recipe feed не исчезает: пользователь получает full-price
варианты. Поэтому supply markdown не блокирует основной контент, но доля
предложений с реальной уценкой измеряется отдельно.

## 6. Целевая аудитория

Рабочий первый сегмент:

> Домохозяйства, которые регулярно покупают ингредиенты для приготовления
> блюд, а не только готовую еду и единичные товары.

Прокси на синтетических данных:

- повторяющиеся cross-category корзины: белок + овощи + молочные/бакалея;
- несколько ingredient-like категорий в одном покупочном цикле;
- сохранение или повтор рецептов;
- покупки short-life staples;
- достаточная история для оценки вкуса, budget и cadence;
- достижимые магазины в выбранном радиусе.

Не требуется угадывать состав семьи, возраст или чувствительные особенности.
Размер порции, исключения, аллергии и `есть дома` задаются явно пользователем.

Внутри ЦА возможны explainable профили:

- `routine` — знакомые блюда и бренды;
- `explorer` — новые кухни и продукты внутри ограничений;
- `value` — максимальная экономия и минимум missing items;
- `time-limited` — короткое приготовление и один достижимый магазин.

## 7. Recommender system

### Candidate generation

Источники кандидатов:

- рецепты с высоким покрытием текущего чека;
- сохранённые рецепты в личном repeat-window;
- новые рецепты из редакционно проверенного каталога;
- новые ингредиенты/SKU, не обязательно встречавшиеся в истории, но близкие к
  наблюдаемым предпочтениям и price band.

Новое не равно рекламе. Как музыкальный recommender предлагает незнакомый трек,
система может предложить новый рецепт без точного аналога в истории. Причина
должна следовать из более общих сигналов: кухни, формата, времени, бюджета,
широты корзины, saves/dismisses и принятия предыдущих discovery-кандидатов.

### Hard gates

- явные food restrictions и исключения;
- редакционно проверенный рецепт;
- допустимые категории;
- достижимый радиус;
- минимум доступных substitutions;
- разумное число и стоимость missing items;
- отсутствие чувствительных выводов из чека.

### Ranking

Сортировка по missing count — важный, но не единственный фактор:

```text
recipe_score = relevance
             + current-basket coverage
             + repeat/discovery fit
             + time/budget fit
             + save/edit feedback
             - missing_count penalty
             - missing_cost penalty
             - constraint violations
```

Рабочее правило интерфейса:

1. кандидаты сначала проходят relevance/safety threshold;
2. внутри сопоставимо релевантных меньше missing items показываются выше;
3. режим `попробовать новое` может осознанно допускать больше missing items;
4. пользователь может пересортировать по `меньше докупить / дешевле / новое`.

Это не позволяет нерелевантному рецепту победить только потому, что для него не
нужно ничего покупать.

### Ingredient → SKU

```text
sku_score = ingredient match
          + personal brand affinity
          + price-band fit
          + substitution history
          + distance/availability
          + markdown preference
          - pack-size mismatch
```

Бренд/SKU может быть знакомым или новым. Supplier payment, advertising bid и
скрытый margin boost не участвуют в organic rank. Если коммерческий контент
появится позже, он должен быть явно маркирован и измеряться отдельно.

### Explainability

Примеры reason codes:

- «5 из 7 ингредиентов уже были в сегодняшнем чеке»;
- «нужно докупить только два продукта»;
- «вы сохраняли похожие быстрые блюда»;
- «это новый рецепт в вашем обычном бюджете»;
- «вы часто выбираете этот бренд»;
- «уценённый вариант сейчас отмечен в магазине в 800 м».

## 8. Радиус и availability

Радиус используется вместо одного домашнего магазина. Он должен учитывать не
только километры, но и фактическую достижимость, если такие данные доступны.

PoC может использовать упрощение:

```text
eligible store = distance ≤ user_radius
```

Система не должна молча собирать один рецепт из нескольких далёких магазинов.
На экране показывается предпочтительный магазин/зона доставки с максимальным
покрытием либо явные альтернативы. Пользователь выбирает `доставка` или
`следующий визит` до финального подтверждения списка.

### Две availability-метрики

```text
store_markdown_availability
  = store-days хотя бы с одним подходящим markdown SKU
    / все store-days

matched_offers_per_user_30d
  = число подходящих и достижимых recipe/markdown offers
    на eligible user за 30 дней
```

Текущий продуктовый ответ — **ежедневная доступность recipe feed**, но не
обещание ежедневной уценки. Отдельно измеряются:

- доля дней с реальными markdown options;
- доля рецептов хотя бы с одним markdown ingredient;
- число релевантных offers/user/30d;
- stock freshness между показом и фактической покупкой;
- доля fallback `markdown → full-price → unavailable`.

Порог достаточности пока не зафиксирован: он выбирается после симуляции и
зависит от того, нужен один дополнительный purchase day или устойчивый цикл.

## 9. Категории и safety

База первого PoC:

- фрукты и овощи;
- молочные продукты;
- мясо;
- другие продукты ограниченного срока, необходимые для базовых блюд.

Для реального пилота список должен пройти category-by-category review. Особенно
для мяса и молочной продукции нужны:

- точная дата/партия и оставшийся safe-use window;
- корректное хранение и cold chain;
- запрет рекомендации после safety cutoff;
- инструкции по хранению и приготовлению из проверенного каталога;
- отсутствие LLM-generated food-safety advice;
- понятное предупреждение об изменении availability.

В PoC эти правила детерминированы и симулируются; модель не отменяет safety gate.

## 10. Домовой без gambling-like слоя

В первые четыре экрана не входят `забрать / рискнуть`, odds и потеря текущего
выигрыша. Домовой работает как спокойный persistent layer:

- продукты из verified-чека появляются в доме;
- выбранные рецепты и пользовательские замены сохраняются;
- приготовленные блюда открывают сцены и предметы;
- дом отражает историю, но не размер трат;
- нет голода, decay, streak и наказания за отсутствие;
- обычная реакция доступна и без покупки уценённого товара.

Gambling-like механика остаётся отложенной гипотезой и не входит в текущий PoC.

## 11. Личный прогресс вместо public rating

Public leaderboard не используется. Экран показывает только личную динамику:

- сколько рецептов сохранено и приготовлено;
- сколько покупочных циклов завершено;
- сколько рублей сэкономлено на фактически купленных markdown items;
- сколько rescue-позиций куплено;
- как изменился дом/аватар.

Формулировка «столько продуктов спасено» требует осторожности: покупка
уценённого товара не доказывает, что без неё он был бы утилизирован. Для PoC
безопасное фактическое название — **«продуктов куплено из rescue-подбора»**.
«Спасено» допустимо только как модельная оценка с явно указанным
контрфактическим допущением.

Личная статистика не используется как causal metric бизнеса и не выдаёт больше
награды за больший объём еды.

## 12. Деньги

### Два денежных маршрута

```text
A. Новый purchase occasion
   recipe save/offer → дополнительный shopping day
   → contribution всей инкрементальной корзины

B. Плановый purchase occasion
   recipe choice → ingredient attach / markdown sell-through
   → incremental whole-basket contribution
```

Маршрут B — реальный business effect, но не заменяет требуемый кейсом рост
частоты.

### Экономика markdown SKU

Для уценённого товара baseline не равен нулю: он мог продаться в текущем канале,
перейти в foodsharing/recovery или списание.

```text
Δrescue_item
  = realized markdown contribution
  - expected baseline value without recommendation
  - incremental serving/data/support/fraud cost
  - displaced regular margin
```

В текущем PoC отсутствуют:

- pick/pack cost отдельного бокса;
- reservation/no-show cost;
- payment/refund flow предоплаты;
- отдельная денежная reward cost.

Для полного recipe basket:

```text
ΔCM_user = contribution дополнительных purchase days
         + incremental contribution ингредиентов в плановых днях
         + incremental rescue value
         - cannibalization/time shift
         - recommender/game/support/fraud costs
```

Для доставки дополнительно учитываются delivery fee, picking и last-mile cost.
Рост заказов доставки не объявляется новым purchase occasion, если это только
перенос той же покупки из магазина в другой канал X5.

Нельзя отдельно сложить маржу каждого ингредиента и маржу всей корзины, если
это один и тот же эффект.

## 13. Метрики

| Уровень | Метрика | Роль |
|---|---|---|
| Case primary | `Δ distinct purchase days/user`, `ΔP(days ≥ N)` на 30/60 днях | ожидаемый кейсом frequency uplift |
| Business | `Δ contribution margin / eligible user` | результат после cannibalization и costs |
| Rescue | incremental value markdown items vs current baseline | проверка пользы уценки |
| Recipe funnel | impression → open → save → list → purchase → repeat | объяснение механизма |
| Personalization | hit rate и own-history vs shuffled-history ≥70% | качество recsys/challenge |
| Availability | store markdown availability, matched offers/user/30d | supply и применимость |
| Game diagnostics | Domovoi opens, scenes, book return | не считаются purchase uplift |
| Trust/safety | opt-out, unavailable rate, complaints, unsafe suggestions | guardrail/kill |

Frequency считается по уникальным дням, а не числу чеков. Рост проверяется на
30/60 днях, чтобы исключить дробление чека и визит сегодня вместо завтра.

## 14. AI и детерминированные правила

| Компонент | Возможная реализация PoC | Что не отдаётся модели |
|---|---|---|
| Recipe candidates | retrieval из проверенного каталога | публикация непроверенной инструкции |
| Recipe ranking | explainable recommender | safety gate и скрытый paid rank |
| Ingredient→SKU | recommender по affinity/price/distance/markdown | персональная цена |
| Mechanic selection | rules/ranker: `current / repeat / explore` | денежная награда |
| Explanation/story | templates или LLM на allowlisted facts | health/family/lifestyle inference |
| Progress | deterministic state transition по verified receipt | начисление за непроверенное действие |

Пример результата:

```json
{
  "mode": "explore",
  "recipe_id": "recipe_128",
  "missing_count": 3,
  "reason_codes": [
    "quick-dinner affinity",
    "new-recipe acceptance: high",
    "usual price band matched"
  ],
  "ingredients": [
    {"category": "milk", "source": "receipt"},
    {"category": "vegetables", "source": "markdown", "distance_m": 800},
    {"category": "meat", "source": "full_price"}
  ]
}
```

## 15. Четыре экрана PoC

### 1. После чека — «Что приготовить»

- продукты из последней покупки приезжают к Домовому;
- top рецептов и объяснение;
- chips `из корзины / повторить / новое`;
- missing count и индикатор доступной уценки.

### 2. Рецепт и сбор ингредиентов

- состав и проверенная инструкция;
- `куплено / есть дома / уценка рядом / full-price / недоступно`;
- сортировка по числу недостающих;
- замены, выбор магазина в радиусе и сохранение плана;
- явное предупреждение: уценка не забронирована.

### 3. Мой план

- выбранный рецепт и shopping list;
- одна рекомендованная точка/зона доставки либо явные альтернативы;
- обновлённая availability;
- выбор `заказать доставку / сохранить к следующему визиту`;
- без отдельной брони rescue-позиции и денежной награды;
- стандартное уведомление при изменении наличия.

### 4. Личная кухня

- новый чек закрывает купленные ингредиенты;
- сохранённый рецепт и сцена Домового;
- прогресс дома/аватара;
- только личные показатели: рецепты, экономия, rescue-позиции;
- referral как отдельная дверь/карточка, без public leaderboard.

## 16. Антифрод и корректность событий

Хотя брони нет, остаются риски чеков, прогресса и referral:

- duplicate receipt ID и replay;
- несколько чеков одного дня ради progress;
- возврат markdown/full-price item после начисления события;
- невозможное совпадение store/time/SKU;
- попытка приписать уценку товару, купленному full-price;
- self-referral, связанные device/payment/account;
- многократная награда за одного invitee.

Precision важнее recall. Сомнительное событие получает `pending/review`, а не
автоматическое обвинение. Все чеки дня схлопываются в один purchase day.

## 17. Эксперимент

Минимальные component arms:

| Arm | Опыт | Что отделяет |
|---|---|---|
| `C0` | текущий опыт | baseline |
| `C1` | персональные рецепты после чека | recipe relevance/utility |
| `C2` | C1 + ingredient list и markdown/full-price выбор | commerce/rescue mediator |
| `C3` | C2 + Домовой, книга и личный progress | game carrier сверх utility |

При достаточном трафике отдельно сравниваются:

- own-history против shuffled/generic recipe;
- ranking только по relevance против relevance + missing count;
- markdown option против тех же рецептов без markdown layer;
- daily in-app feed с capped push policy против feed без push.

Primary — purchase days / `P(≥N)`. Business outcome — contribution/user.
Recipe saves, markdown clicks и Domovoi return остаются diagnostics.

## 18. Симуляция на 1–10 тысячах пользователей

Сущности:

- users: cooking affinity, mode, budget, radius, cadence, brand affinity;
- receipts: store/day/SKU/category/price/markdown;
- recipes: ingredients, time, categories, verified status;
- stores: location и synthetic availability full-price/markdown;
- fulfillment: delivery coverage/cost или следующий store visit;
- events: impression, save, substitution, purchase, repeat, progress, referral.

Base-case не предполагает uplift:

```text
Δpurchase_days = 0
game uplift = 0
markdown incrementality = 0 до заданного counterfactual
```

Сценарии меняют:

- relevance и save rate;
- missing-count distribution;
- markdown availability в радиусе;
- fallback в full-price;
- conversion списка в чек;
- выбор delivery/visit и channel shift между ними;
- долю отдельного дня против плановой корзины;
- cannibalization/time shift;
- contribution и fraud loss.

Выход: воронка, `Δpurchase days`, `P(≥N)`, contribution/user, rescue value,
availability, hit rate и sensitivity к ключевым допущениям.

## 19. Kill / simplify criteria

- own-history и персональный top не достигают 70% relevance;
- missing-count сортировка вытесняет более релевантные рецепты;
- пользователи воспринимают список как скрытый cross-sell;
- markdown availability слишком мала и full-price fallback превращает rescue в
  обычную витрину;
- availability без брони слишком часто устаревает;
- recipe list растит basket CM, но не частоту — тогда это secondary module;
- Домовой растит только game/app retention, не покупки/contribution;
- предложения short-life products повышают complaints или consumer waste;
- эффект исчезает на 30/60 днях или вызван split/time shift;
- contribution/user ниже control после cannibalization и costs.

## 20. Оставшиеся вопросы команды

- Какой радиус допустим и как выбирать одну точку/зону доставки среди
  нескольких?
- Какая максимальная доля missing ingredients допустима в режиме `новое`?
- Как оценивать свежесть markdown availability без брони?
- Какие категории из базы безопаснее взять первыми, особенно мясо и молочные?
- Как именно определить `приготовленный рецепт`, если это self-reported action?
- Называем ли личный показатель «спасено» или только «куплено из rescue»?
- Нужен ли referral в основном пользовательском сюжете либо только для
  выполнения обязательного требования кейса?
- Какой core остаётся, если markdown почти всегда заменяется full-price?
