# Чувствительность к нашим допущениям

> Исследовательский материал ML-ветки, сохранённый при интеграции 06.09.2026.
> Код стенда использует `recsys.experimental`; приведённые числа и предложения
> не являются результатами или принятыми контрактами мобильного API 1.2.
> [Границы и актуальные пути](https://github.com/x5-loyalty-hackathon/x5_loyalty_system/blob/experiment/vxofi/recsys/experimental/README.md).

Сгенерирован `python -m recsys.sensitivity`. 7 ручек × 3 значений, по 80 пользователей на мир, 0 с.

Вопрос не «как поедут числа», а **перевернётся ли вывод**. Вывод, устойчивый к движению ручки от края до края, от этой ручки не зависит — и спорить о её значении не нужно. Вывод, который переворачивается, — это вопрос кейсодателю, и он заслуживает времени на встрече.

---

## 0. Устойчивость самой развёртки (читать первым)

Развёртка имеет смысл, только если её точка отсчёта не пляшет сама по себе. Здесь базовая настройка прогнана на трёх сидах: если вывод меняется между ними, строки про него ниже читать нельзя.

| Вывод | Одинаков на всех сидах |
|---|:--:|
| стенд отличает осмысленное ранжирование от шума | да |
| под текущей политикой модель лучше случайной | да |
| когда политика пропускает ранжирование, модель лучше случайной | да |
| есть рука, заметно опережающая остальные | да |
| эвристика не хуже модели | да |

Все выводы воспроизводятся на всех сидах.

## Итог: что спрашивать у эксперта

| Вывод | Устойчив к | Ломается от |
|---|---|---|
| стенд отличает осмысленное ранжирование от шума | 3 из 7 ручек | `no_product_at_all`, `out_of_stock`, `time_value`, `within_radius` |
| под текущей политикой модель лучше случайной | 6 из 7 ручек | `no_product_at_all` |
| когда политика пропускает ранжирование, модель лучше случайной | 5 из 7 ручек | `no_product_at_all`, `within_radius` |
| есть рука, заметно опережающая остальные | 7 из 7 ручек | **ничего** |
| эвристика не хуже модели | 7 из 7 ручек | **ничего** |

**Ручки, которые вообще что-то ломают, по убыванию влияния:**

- `no_product_at_all` — Как часто нужного ингредиента нет в магазине вообще?
  - ломает: стенд отличает осмысленное ранжирование от шума; под текущей политикой модель лучше случайной; когда политика пропускает ранжирование, модель лучше случайной
- `within_radius` — Какая доля предложений попадает в радиус доставки пользователя?
  - ломает: стенд отличает осмысленное ранжирование от шума; когда политика пропускает ранжирование, модель лучше случайной
- `time_value` — Сколько стоит час готовки для покупателя?
  - ломает: стенд отличает осмысленное ранжирование от шума
- `out_of_stock` — Как часто товар есть в каталоге, но закончился на полке?
  - ломает: стенд отличает осмысленное ранжирование от шума

**Ничего не ломают** (значение можно не уточнять): `markdown_offered`, `price_level`, `missing_tolerance`.

## Влияние на ценность продукта (это другой вопрос)

Раздел выше отвечает: «изменится ли **вывод о ранжировании**». Он молчит о том, есть ли продукт вообще. Это разные вопросы, и путать их опасно: ручка может не менять ни один вывод и при этом решать судьбу проекта.

| Ручка | готовок на юзера: мин → база → макс | размах |
|---|---|---:|
| `markdown_offered` | 0.145 → 0.196 → 0.267 | +83% |
| `no_product_at_all` | 0.147 → 0.196 → 0.225 | +53% |
| `out_of_stock` | 0.156 → 0.196 → 0.207 | +33% |
| `within_radius` | 0.113 → 0.196 → 0.276 | +145% |
| `price_level` | 0.072 → 0.196 → 0.449 | +525% |
| `time_value` | 0.069 → 0.196 → 0.308 | +350% |
| `missing_tolerance` | 0.183 → 0.196 → 0.220 | +20% |

**Читать так:** большой размах при устойчивых выводах означает «на выбор алгоритма не влияет, на бизнес-кейс влияет сильно». Такую ручку всё равно нужно уточнять у кейсодателя — просто не ради выбора модели, а ради оценки самой затеи.

## Оговорки

- Диапазоны ручек выбрали мы. Они широкие, чтобы **содержать** правду, а не угадать её.
- Прогон меньше основного (по 80 пользователей, 9 миров): цель — устойчивость вывода, а не третий знак после запятой.
- Ручки крутятся по одной. Взаимодействия между ними не проверены: две безобидные по отдельности могут ломать вывод вместе.
- Колонка «готовок на юзера» намеренно не «конверсия на карточку». При дефиците карточек становится меньше, а выживают лёгкие — конверсия на карточку растёт, тогда как готовок на человека падает. Между настройками сравнимо только на пользователя.
