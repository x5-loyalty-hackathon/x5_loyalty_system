## P1. Расхождения, которые исправляем по нашему контракту

| Область | Фактическое состояние | Что требуется при интеграции |
|---|---|---|
| Вход в продукт | Приложение начинается с кухни; переход к рецептам есть, контекста доставки рядом с входом нет | Встроить согласованный вход до подбора товаров; не создавать ещё одно самостоятельное приложение/новую большую ветку экранов |
| Серверная выдача | При успешном ответе API локальные рецепты дописываются в результат, статус остаётся `live` | В живом режиме показывать только прошедшую backend-проверки выдачу; пустой результат не заполнять локальными кандидатами. Демо-режим отделить явно |
| Режимы и объяснения | UI группирует старые `RecipeRecommendation`; `challenge_selection`, default, opt-in и причины не используются | Подключить meal API 1.2 и использовать решение сервера; полная новая корзина требует явного выбора |
| Блюдо и товары | `readyMeal` и замены берутся из локального каталога; серверные `product_options` и предупреждения теряются при преобразовании | `cook/ready` — варианты одного блюда; товары, точка, доступность и уценка идут из проверенного ответа, а не параллельной локальной выдачи |
| Покупка и готовка | Отправляется один фиксированный чек с молоком и `recipe_completed=true`; содержимое локальной корзины в запрос не попадает | Сохранить meal-план, отправить соответствующий ему синтетический чек; для готовки — отдельное подтверждение, для готового — подтверждённая покупка выбранного SKU |
| Книга и наличие дома | Сердце в рецепте — декоративный `View`; изменение наличия только локальное | Подключить существующую книгу API; поправка наличия должна влиять на повторный расчёт. Не превращать это в полноценную систему учёта холодильника |
| Магазин и уценка | Fixture задаёт 3 км, товары в 0.8/1.4 км, без уценки; mobile-документы говорят, что уценку исключили | Сохранить наш контекст `home/work/current/custom`, 750 м как demo-default, ручной выбор и одну точку. Вернуть опциональную уценку и предупреждение о небронированном товаре |
| Домовой | Есть графика кухни и отображение числового прогресса; состояния выбора предметов нет | Выбираемое оформление реализовать в пределах согласованного Б2; каталог по уровням пока не считать утверждённой большой системой |

### Подтверждённые диагностические примеры

- Отправка **реального fixture мобильной ветки** в наш API 1.2 возвращает
  `verified`, 1 приготовленный рецепт, 100 ₽ экономии и 30 XP, хотя meal-план
  отсутствует. Это поддержанный legacy-путь, а не подтверждение нового flow.
  Вторая отправка возвращает `duplicate`: награда защищена от повтора, но новый
  сценарий нельзя показать повторной отправкой того же фиксированного чека.
- При `missing.length === 0` кнопка «начать готовить» всё равно вызывает
  `openProducts()` и ведёт к покупке. Нужен путь без искусственной докупки.
- На главном экране текст «Молоко надо выпить сегодня» и кухонные остатки —
  локальный демо-контент. Не выдавать его за вычисленный по чекам срок годности.
- Web-preflight с `Origin: http://localhost:8081` к нашему API возвращает
  **400**. Для браузерного Expo smoke понадобится явно разрешённый локальный
  origin; это не блокер CORS для нативного Expo Go.

`mobile/docs/api-gaps.md` не становится новым заданием backend автоматически:
meal-рекомендации, планы, готовый route, книга и выбор точки у нас уже есть.
Действительно требуется согласовать передачу проверенного контента карточки
(описание, шаги, количества/порции) и поправок наличия. Отдельные промышленная
корзина X5, вычисление срока домашних остатков и универсальный API замен не
следуют из принятого PoC.

## ML: что сохраняем и что адаптируем

Полезные добавления: расширенный каталог с порциями и количеством ингредиентов,
маркировка оценочных цен, пары «рецепт — готовое блюдо», несколько политик
ранжирования, парные сравнения на общей синтетике, разные модели реакции и
отрицательный контроль. Это развитие прежнего smoke, но не новая модель,
обученная на реальных решениях покупателей: обучение по-прежнему синтетическое.

**Нельзя переносить ветку целиком поверх нашего backend:**

- удалены `home_ingredient_ids` и источник `home`, в том числе из признаков и
  генератора профилей — это расходится с принятым поведением;
- используется старый API 1.0 без нашего выбора стратегии, meal-планов и
  одной точки; стенд вызывает именно этот сервис;
- `ReadyMealOption` — каталоговый кандидат без магазина, расстояния, наличия,
  срока и состава. Его нельзя показывать как проверенный доступный `ready`.
  В прямом диагностическом запросе вариант возвращается даже при пустом
  `inventory_snapshot`; фильтрация готового товара по ограничениям пользователя
  не выполняется. Нужен перенос через наш safety-контур, а не его обход;
- новый proposed ADR имеет номер `002`, уже занятый нашим accepted meal-ADR.
  При переносе ему нужен отдельный уникальный номер и сохранение статуса
  предложения. Default ранжирования не меняем ради результата симуляции.

Предварительный read-only merge-анализ показал конфликты в `app/contracts.py`,
`app/service.py`, `docs/decision-log.md`, `docs/technical-design.md`,
`recsys/examples/sample_recommendations.json`, `recsys/reason_codes.py`,
`tests/test_api.py`. Удаление поддержки `home` может примениться автоматически
без конфликта: отсутствие маркеров merge не означает сохранение смысла.
У `origin/main` относительно нашей ветки текстовых конфликтов не обнаружено;
это не проверка работоспособности объединённого приложения.

### Границы нового evidence

1. Стенд оценивает реакции **на отдельные карточки**, а не контакт с человеком
   до покупки, последовательность визитов, отменённые следующие закупки или
   эффект на покупочные дни. `cook_conversion_rate` допустима как диагностика
   рецептов, но не как основная метрика нашего meal-first продукта. Успешный
   `ready` не является автоматически плохой рекомендацией.
2. В economic-симуляторе `missing_count == 0` может дать действие `BUY`: это
   ещё один довод не переводить счётчик реакций в число новых покупок.
3. По умолчанию работают три алгоритмических симулятора и самореферентный
   oracle. `LLMResponder` — интерфейс с передаваемой функцией, без подключённой
   модели; LLM-покупатели в опубликованном прогоне не участвовали.
4. Есть воспроизводимый дефект seed: `RandomEngine` и stochastic responder
   используют Python `hash()` со строкой. При одном seed=7 и одинаковых трёх
   кандидатах `PYTHONHASHSEED=1` даёт порядок `b,a,c`, а `=2` — `c,a,b`.
   Существующий тест запускает сравнение внутри одного процесса и этого не
   ловит. Нужны стабильное формирование seed и межпроцессный тест.
5. Числа опубликованного benchmark-отчёта в этом разборе **не воспроизведены**:
   отсутствуют runtime-данные. После адаптации к API 1.2 выводы старого прогона
   не переносятся автоматически — проверяется конечная новая выдача.

Источники: [действия симулятора](https://github.com/x5-loyalty-hackathon/x5_loyalty_system/blob/2b3f73b/recsys/response_models.py#L284),
[интерфейс LLM](https://github.com/x5-loyalty-hackathon/x5_loyalty_system/blob/2b3f73b/recsys/response_models.py#L327),
[seed ранжировщика](https://github.com/x5-loyalty-hackathon/x5_loyalty_system/blob/2b3f73b/recsys/benchmark.py#L94),
[проход по карточкам](https://github.com/x5-loyalty-hackathon/x5_loyalty_system/blob/2b3f73b/recsys/benchmark.py#L418).

## Порядок интеграции и проверок

1. **Восстановить публикацию данных.** Мобильный файл уже добавлен и сборка
   проверена; остаются два ML-файла. Проверяем снимки из Git, а не наличие
   файлов только на авторской машине. ML не блокирует адаптацию UI на mock.
2. **Собрать frontend с нашим backend.** Сохранить макеты, заменить адаптер
   старых трёх запросов на API 1.2; сначала один `cook` и один `ready` flow на
   известных fixtures. Модель для этого не обязательна, режим mock виден явно.
3. **Перенести ML через совместимость с нашим контрактом.** Сохранить `home`,
   selection, single-store и safety; добавить данные/метаданные и перенести
   стенд. Не подменять доменный контракт копией файлов из ML-ветки.
4. **Проверить сквозной сценарий.** Вход рядом с доставкой → выбор блюда/route
   → книга/план → соответствующий чек → отдельное завершение готовки → личный
   прогресс. Уценка и обычная цена — варианты того же ингредиента.
5. **Повторить evidence на общей версии.** Автотесты, сравнительный стенд,
   явные ограничения и демонстрация. [Q13 / план пилота](../pilot-plan.md)
   остаётся обязательным; открытия, cook-реакции и synthetic scores не
   подменяют покупочную метрику.

Минимальные новые test gates для шагов 2–4:

- пустой/отфильтрованный API-ответ не заполняется локальными рецептами;
- default, альтернативы и полная корзина соответствуют `challenge_selection`;
- `save → repeat` работает после нового запроса, без начисления за сохранение;
- поправка «продукт закончился» меняет докупку; при всём имеющемся нет
  принудительного перехода в покупку;
- выбор `work`/магазина соблюдается; одна cook-корзина не смешивает точки;
- исчезновение уценки не теряет план и не сохраняет старую цену молча;
- synthetic-чек соответствует выбранным товарам; `cook` и `ready` завершаются
  по своим правилам; дубликат не даёт вторую награду;
- сравнение с одинаковым seed воспроизводится в разных процессах.

Это план следующих изменений, не список уже написанных или пройденных тестов.
В данном разборе код, ветки и remote PR не изменялись. Подготовлены только
документы; отсутствующие авторские данные не заменялись заглушками.
