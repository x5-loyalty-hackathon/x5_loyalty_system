# Продуктовый материал 3. Вклад AI Product и его влияние на техническую реализацию

- **Статус:** промежуточная версия, 03.09.2026.

Этот документ показывает, какие решения приняты в продуктовом контуре и как
каждое из них уже изменило код, схемы или тесты — а не осталось слайдом.

## 1. Что сделал AI Product до промежуточной сдачи

1. **Сформулировал нулевую гипотезу.** Исследование российского grocery,
   смежных отраслей и международных кейсов (включая свёрнутые и пострадавшие от
   фрода программы) дало вывод: игра, коллекция или аватар сами по себе не дают
   incremental uplift. Это стало рамкой отбора идей.
2. **Развернул концепцию с физического бокса на recipe-first.** Ранняя версия
   предполагала собранный магазином rescue-набор с бронью и pickup. Продуктовый
   анализ показал, что это добавляет сборку, предоплату, no-show и удержание
   товара — и был выбран цифровой recipe plan.
3. **Определил сегмент и профили** (`routine / explorer / value / time-limited`)
   через наблюдаемые сигналы корзины, без чувствительных выводов о пользователе.
4. **Задал метрическую рамку:** primary — уникальные дни покупок, guardrail —
   contribution/user, игровые метрики — только диагностика.
5. **Определил границы AI:** что модель решает, а что остаётся детерминированным.
6. **Зафиксировал решения в ADR-001** и разложил их на обязательные test gates.

## 2. Как продуктовые решения изменили техническую реализацию

| Продуктовое решение | Прямое следствие в коде |
|---|---|
| Уценка — опция внутри рецепта, а не отдельный лот | в `app/service.py` markdown/full-price варианты прикладываются **только** к ингредиентам рецепта; out-of-recipe SKU не возвращаются |
| Брони и предоплаты нет | в ответе API обязательный no-reservation warning; тест проверяет его наличие |
| Релевантность важнее числа докупок | порядок сортировки в сервисе: сначала safety-фильтр, затем `missing_count ASC`, затем `model_score DESC`; модель отвечает за relevance eligibility |
| Модель не может отменить безопасность | `app/safety.py` применяется **после** ранжирования; тесты на expired / unsafe / out-of-radius / exclusions |
| Нет публичного рейтинга, ФИО и адресов | в `app/progress.py` отдаётся только собственная позиция, размер когорты и перцентиль; leaderboard-эндпоинта не существует, это закреплено тестом |
| Нет денежной награды | реферальная награда в `app/referral.py` — виртуальный прогресс с `monetary_value=0` |
| Частота считается по уникальным дням | `app/state.py` схлопывает все чеки одного дня в один purchase day |
| Precision важнее recall | `app/fraud.py`: неоднозначные device/payment-совпадения уходят в `pending_review`, hard-block только на явном пороге |
| Ограничения задаёт пользователь явно | в схеме запроса есть явные исключения; backend не делает health/family/lifestyle inference |
| Food safety не генерируется LLM | инструкции берутся из проверенного каталога; safety-правила детерминированы и покрыты тестами |
| Коммерция не влияет на organic rank | commercial metadata отсутствует в model/API контракте |

## 3. Границы AI и детерминированных правил

| Компонент | Отдано модели | Не отдаётся модели |
|---|---|---|
| Кандидаты рецептов | retrieval из проверенного каталога | публикация непроверенной инструкции |
| Ранжирование рецептов | explainable recommender | safety-гейт и скрытый платный ранг |
| Ингредиент → SKU | affinity, price band, distance, markdown | персональная цена |
| Выбор механики | `current / repeat / explore` + reason codes | денежная награда |
| Объяснение и текст | шаблоны или LLM по allowlisted фактам | выводы о здоровье, семье, образе жизни |
| Прогресс | — | детерминированный переход состояния по verified-чеку |

Правило, зафиксированное в архитектуре: **AI ранжирует, детерминированные
правила разрешают.** Модель не может протолкнуть небезопасный, просроченный,
недоступный или исключённый пользователем товар высоким score.

## 4. Объяснимость как продуктовое требование

Кейс требует объяснимого выбора механики. Reason codes являются частью
контракта API, а не UI-текстом:

```json
{
  "recipe_id": "recipe_128",
  "mode": "explore",
  "score": 0.82,
  "missing_count": 3,
  "reason_codes": ["quick_dinner_affinity", "discovery_acceptance_high"]
}
```

Пользователь видит формулировки вида «5 из 7 ингредиентов уже были в сегодняшнем
чеке», «нужно докупить только два продукта», «это новый рецепт в вашем обычном
бюджете», «уценённый вариант отмечен в магазине в 800 м».

## 5. Что честно не сделано в продуктовом контуре

- нет интервью и качественной валидации с реальными покупателями;
- пороги достаточности availability не зафиксированы — выбираются после
  симуляции;
- формулировка «спасено продуктов» пока не принята: используем «куплено из
  rescue-подбора»;
- решение, нужен ли реферал в основном сюжете или только для выполнения
  требования кейса, не принято;
- одностраничный план пилота — работа до 06.09.
