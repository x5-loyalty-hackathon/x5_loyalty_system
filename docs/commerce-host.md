# Граница игры и оформления магазина

Принято `vxofi` 07.09; [план и сверка PR #9](reviews/2026-09-07-pr9-fix-plan.md).
Это уточнение сценария, **не новая промышленная интеграция**.

## Сценарий

Выбрать блюдо → выбрать продукты → **«К оформлению» в приложении магазина**.
После принятого чека: рецепт — **Кухня → «Готовить» → «Я приготовил»**;
готовое блюдо — завершение по чеку и личный прогресс.

Каталог, обычная корзина, адреса, доставка и оплата принадлежат основному
приложению. Игра не добавляет свои адреса/кассу/платёжное окно. «Мой план»
показывает товары блюда, не заменяет всю корзину магазина. При интеграции эти
позиции добавляются к обычной корзине, не удаляя остальные.

Черновик обновляется автоматически в `DemoContext`: выбор товаров не требует
POST и кнопки «Сохранить». Кухня/выдача/возврат к тому же блюду сохраняют выбор
в сессии. Другое выбранное блюдо заменяет текущий игровой черновик. История
нескольких заданий и восстановление после перезапуска не реализованы;
долговременное хранение основной корзины — задача приложения.

## Где код

- `mobile/src/domain/commerce.ts`: `CommerceHost.openCheckout(request)`.
  Native-оболочка передаёт `commerceHost` в `DemoProvider`; web-оболочка может
  установить `globalThis.__X5_COMMERCE_HOST__`.
- `DemoContext.checkout`: проверяет корзину, активирует задание по серверному
  `offer_id`, передаёт снимок SKU/fulfillment основному приложению.
- `products.tsx`: обработчик нижней кнопки — только `checkout`. После покупки
  кнопка отключена, чек/готовка из неё не запускаются.
- `DemoContext.acceptPurchase`: проверяет user/plan события приложения,
  отправляет его в receipt API, получает серверные план/XP и обновляет Кухню.
- `index.tsx`: существующее действие плана открывает готовку после сборки
  продуктов; завершённое ready-задание ведёт к прогрессу.

Запрос содержит `checkoutId`, `plan`, `products`. **Приложение обязано использовать
checkoutId как ключ идемпотентности:** повтор возобновляет ту же попытку, а не
создаёт второй заказ. Это обязанность реального адаптера, не доказанная защита
промышленного заказа со стороны нашего PoC.

| Результат обработчика | Что делает игра |
|---|---|
| `{status: 'cancelled'}` | Подтверждённая отмена без покупки. Сохраняет редактируемый черновик, не создаёт чек/XP. Следующая попытка активирует новый неизменяемый план. |
| `{status: 'purchased', receipt}` | Событие покупки с теми же user/plan ID. **Не** открытие оплаты/создание заказа. Receipt API проверяет основания; cook ещё требует готовки, ready — нет. |
| Ошибка/неизвестный результат | Сохраняет точную попытку, блокирует изменение её состава до повторения. Если потерян ответ receipt API, повторяет только тот же чек, не оформление. |

Отмена не удаляет уже созданное задание из серверного счётчика планов:
cancel endpoint нет. Это **не покупочная метрика**. Поздний ответ после смены
demo-профиля не меняет новую сессию. Лимит ADR-005 и серверная проверка XP прежние.

## Как проверять и демонстрировать

**В репозитории нет основного приложения и его оформления.** Без адаптера кнопка
показывает это в существующем блоке сообщений; заказ, чек и задание не создаются.
Полностью автономный ручной показ покупки на телефоне требует отдельно
подключённой демонстрационной оболочки. Новые кнопки/экраны для неё не добавлены.
Готовка из текущих покупок работает без оформления.

`mobile/scripts/browser-commerce-smoke.mjs` — **отдельный синтетический host-драйвер**:
управляет реальным web UI, раздельно подтверждает/отменяет внешнюю покупку,
не добавляет экран и не включён в runtime приложения. Запуск из `mobile`:

```sh
# Чистый backend и Expo web по README; Node 24, Playwright установлен отдельно.
X5_SMOKE_URL=http://localhost:8081 node scripts/browser-commerce-smoke.mjs
```

Если Playwright не установлен локально: `X5_PLAYWRIGHT_MODULE` — путь к его
`index.mjs`. `X5_SMOKE_SCREENSHOT` — абсолютный путь выходного PNG. Тест headless,
требует чистый backend: проверяет 20 XP после cook и 0 добавочных после ready
в тот же покупочный день. Mock/model API-проверки работают без браузера/адаптера:
`npm run test:api`, `X5_TEST_ENGINE=model npm run test:api`.

Ограничения: process-local backend и клиентская сессия; синтетическое, не
промышленное подтверждение; нет реального адресного контекста, оплаты, статусов
заказа, возвратов, замен и нескольких доставок одного заказа. Частичный чек
не отображается как покупка всей корзины. GET кухни/инструкций и долгоживущая
история заданий остаются отдельным следующим этапом.
