# ADR-005: игровые задания и XP с подтверждением покупки

- **Дата:** 2026-09-06.
- **Статус:** accepted для PoC. При разрешении реализовать план 06.09 принят
  консервативный demo-предел §6: один бонус на покупочный день.
- **Основание:** `vxofi` согласовал XP за выбранное игровое задание с покупкой,
  отказ от автоматических покупочных XP и сохранение входа после кассы;
  затем запросил проработку разнообразия и фиксацию контракта.
- **Состояние:** правило награды реализовано в API **1.3**, включая `offer_id`,
  проверку покупки, лимит и UI-объяснения. Полноценный выбор декора и новые
  сцены остаются отдельным следующим инкрементом, не результатом этого исправления.
- **Связи:** [meal-flow](002-personal-meal-contract.md),
  [стратегии](003-challenge-mode-selection.md),
  [книга и магазин](004-recipe-book-and-shopping-context.md).

## 1. Решение в одном абзаце

Пользователь выбирает, что сделать вместе с Домовым, и выполняет задание,
опирающееся на подтверждённую покупку. За это получает общий XP к выбранному
оформлению дома, а не обязательный предмет за конкретный рецепт. Чек сам по себе
не приносит покупочные XP; отметка «приготовил» сама по себе — тоже. Покупка
доказывает участие в покупке, **не факт приготовления**. Рецепты, книга и
взаимодействие с Домовым доступны и без новой покупки, но не позволяют
неограниченно получать XP.

## 2. Нужно ли разнообразие заданий

**Да, на уровне цели и личной истории; отдельные мини-игры для PoC не нужны.**
Минимальная рамка для реализации — три варианта уже принятого meal-задания:

| Стратегия | Рабочее название и цель | Взаимодействие и результат |
|---|---|---|
| `current` | «Ужин из моих покупок»: использовать подходящие продукты текущего чека | Выбрать посильное блюдо из имеющегося; после выполнения оно появляется в сцене/истории Домового |
| `repeat` | «Наш любимый ужин»: вернуться к сохранённому рецепту | Выбрать знакомое блюдо; Домовой отмечает возвращение к нему, запись связывается с тем же рецептом |
| `explore` | «Новое для нашей кухни»: выбрать подходящий новый рецепт | Осознанно выбрать новое предложение; после выполнения оно появляется в истории, рецепт можно сохранить |

Это не три новые механики с разной экономикой и не три обязательных квеста.
Названия — рабочий UX-copy; сцена/реакция может быть простой, без нового экрана,
генерации арта или отдельного игрового движка. Смена названия сама по себе не
доказывает разнообразие: должны различаться причина предложения и личный контекст.

- Сохраняются правила ADR-003: один default, до двух подходящих альтернатив;
  не заполняем три слота любой ценой и не заставляем чередовать режимы.
- Один рецепт может подходить нескольким стратегиям. Смена mode не создаёт
  новую награду. Внутри явно выбранного режима допустимы несколько рецептов.
- В текущей модели `explore` означает отсутствие рецепта в сохранённой книге,
  а не доказанное «вы никогда это не ели». Интерфейс не делает такого утверждения.
- `cook / ready` — способы выполнения meal-задания, не четвёртый режим.
  Для `ready` нельзя обещать готовку; подходит формулировка «Ужин без готовки».
- Уценка — добровольный выбор продукта внутри рецепта, не отдельное обязательное
  задание и не множитель XP. Full-price остаётся допустимым fallback.
- Никаких заданий «купи больше», случайного обязательного бренда, платного входа,
  штрафа за пропуск дня, обязательного streak или закрытых уровнем рецептов.

Разнообразие здесь — продуктовая гипотеза о полезности и интересе, не измеренный
эффект. Дополнительные мини-игры, коллекции и социальные задания — после PoC,
только если станет понятно, какое действие пользователя они улучшают.

## 3. За что даём XP

| Событие | Покупочные / meal XP по новому правилу |
|---|---|
| Чек получен, но игровое задание не выбрано | **0 XP**; покупочный день и подтверждённая экономия учитываются отдельно |
| Открытие игры, просмотр карточки, сохранение в книгу, выбор задания | **0 XP** |
| Выбран `cook`, необходимые покупки подтверждены, пользователь отметил приготовление | **20 XP**, если выполнены условия §5 и не исчерпан предел §6 |
| Выбран `ready`, подтверждена покупка соответствующего готового блюда | **20 XP** при тех же условиях; кнопка «я поел» не требуется |
| Приготовление только из домашних запасов без подходящего покупочного подтверждения | **0 XP**; готовка и личная история остаются доступны |
| Повтор запроса, новый plan ID или другой mode для уже вознаграждённого основания | **0 дополнительных XP** |

Автоматические **10 XP за покупочный день отменяются** как целевая политика.
Покупочные дни, рецепты, готовые блюда и награждённые задания — разные счётчики.
Формула `purchase_days × 10 + meals_completed × 20` больше не является целевой.

**20 XP за задание и 50 XP на уровень** сохраняем как прежние demo-значения,
не как проверенную настройку экономики или темпа игры. XP накопительный,
без денежного эквивалента. Возможность выбрать оформление не привязывается к
конкретному блюду; новый тратящийся баланс/валюта не вводится. После ответов
D1–D2 добавлен [контракт C6](../home-decoration-contract.md): отдельные обои,
выбор цели и свободное применение открытого варианта. Это минимальный каталог,
не полный магазин декора; проверка реализации отмечается во
[второй волне](../reviews/2026-09-06-poc-wave-2.md).

**Рефералка — отдельная ранее принятая механика:** по 20 XP участникам после
первой подтверждённой покупки приглашённого, однократно. Этот ADR её не меняет;
предел meal-награды к ней не относится. Запрет пассивных XP выше относится к
обычному чеку, а не отменяет ранее согласованную реферальную награду.

## 4. Два входа, а не требование всегда планировать до кассы

**После покупки — первый полезный игровой опыт:**

```text
подтверждённый текущий чек → вход в игру → выбор задания
→ при необходимости докупка → выполнение → XP, если есть право на награду
```

Рецепт может быть выбран после чека. Для награды сервер использует именно
подтверждённый текущий чек, лежавший в основании выданного предложения, а не
произвольный чек, выбранный клиентом задним числом. Если нужна докупка, одного
пересечения с исходным чеком недостаточно: обязательная корзина должна быть собрана.
В `ready` уже купленное подходящее блюдо может закрыть явно выбранное задание;
до выбора задания автоматической meal-награды нет.

**Следующий ужин — гипотеза влияния на новую покупку:**

```text
вход в игру → выбор следующего ужина → список необходимых продуктов
→ доставка или следующий визит → подтверждённая покупка → выполнение → XP
```

Покупка для этого продолжения должна произойти после выбора задания. Старый
чек не закрывает новые покупки. Исключение для текущего чека — только первый
путь выше, а не отключение проверки времени у всех планов.

Приготовить позже можно: день покупки и день нажатия «приготовил» не обязаны
совпадать. Нет ежедневного требования зайти в игру. Не выдумываем недостающий
ингредиент, если всё уже есть, и не блокируем готовку из-за отсутствия XP.

## 5. Условия награды и граница доверия

Завершение блюда и право на XP проверяются отдельно. Награда разрешена, когда
одновременно выполнены следующие условия:

1. **Есть явный выбор задания.** Сохранение выбранного meal-плана означает
   активацию; отдельная обязательная кнопка «забрать XP» не нужна. Сохранение
   рецепта в книгу не равно активации задания.
   Уточнение 07.09: сохранение плана — **внутренняя операция** перед передачей
   товаров в обычное оформление приложения либо перед готовкой, когда всё есть.
   Отдельного шага «Сохранить план» нет. Открытие/отмена оформления не подтверждают
   покупку. [Граница игры](../commerce-host.md).
2. **План принадлежит пользователю и соответствует реально выданному офферу.**
   Сервер сохраняет основание рекомендации и разрешённый выбор рецепта/route/SKU.
   Переданные клиентом ID, домашние запасы или режим не могут сами создать право
   на награду. HOME остаётся явной пользовательской отметкой, не доказательством покупки.
3. **Есть подходящая подтверждённая покупка этого пользователя.** Для `cook`
   чек содержит обязательный ингредиент выбранного блюда, а все необходимые
   докупки закрыты; для `ready` — выбранный или заранее разрешённый готовый SKU.
   Посторонний товар, необязательный гарнир и просто `receipt_id` не подходят.
   Продукты, отмеченные «есть дома», не подменяют покупочное подтверждение.
4. **Route завершён.** Для `cook` это отдельное заявление «приготовил» после
   сборки; для `ready` — совпадение подтверждённого чека и выбранного задания.
   Открытие шагов, просмотр рецепта и фото еды не являются проверкой готовки.
5. **Основание ещё не вознаграждено и доступен лимит.** Запись награды и проверка
   ограничения выполняются атомарно. Другой plan ID, режим, route, повторная
   отправка или гонка запросов не умножают XP.

Доказательство покупки должно храниться сервером: user, чек, время покупки,
подходящие позиции и связь с выбранным заданием. Текущий список
`selected_product_ids` содержит лишь докупку и сам по себе недостаточен для
`current`, полностью закрытого исходным чеком. Пустая докупка не означает ни
«награда положена», ни «пользователь обязан что-то докупить».

В PoC это всё ещё **синтетические подтверждённые события**. Нет интеграции с
кассами и production-auth; антифрод и связь с оффером не превращают клиентский
JSON в доказанную реальную покупку. Покупочные и временные основания не должны
конструироваться UI специально ради обхода ограничения даже в demo.

## 6. Предел meal-наград в PoC

**Принятый demo-предел:** один бонус 20 XP на пользователя за
подтверждённый покупочный день, независимо от числа чеков, блюд и режимов.
Альтернатива — один бонус на отдельный использованный чек; она допускает
увеличение награды дроблением покупки, поэтому не рекомендуется.

Правила:

- день определяется по времени **покупки**, в `Europe/Moscow`, не по времени
  завершения готовки и не по переданному клиентом «дню задания»;
- опорный чек — исходный текущий, если докупки не нужны. Иначе все связанные
  подходящие чеки сортируются по времени покупки (при равенстве — по ID):
  опорным становится первый чек, после которого суммарно закрыты все докупки.
  Поздняя повторная покупка уже закрытого ингредиента не переносит день награды;
- до завершения задания основание пересчитывается при поступлении подходящего
  чека, в том числе перекрывающего уже известные позиции. Для одинакового набора
  чеков, принятых **до завершения**, порядок доставки не меняет покупочный день;
- награда использует день этого чека. Если блюда хватает на несколько дней,
  повторная готовка не создаёт новых покупочных оснований;
- если план собирается несколькими чеками, он всё равно даёт одну награду;
  при завершении основание фиксируется, даже если бонус равен нулю. Более поздние
  события не пересчитывают завершённое задание и не дают повторную награду.
  Для `ready` завершение происходит сразу на подходящем чеке / выборе после кассы:
  ещё не поступившие на этот момент события нельзя считать известными серверу.
  Остальные продукты могут участвовать в других рецептах: расход граммов в PoC
  не доказан. Повтор готовки в новый день сам по себе лимит не обновляет;
- без участия в игре покупка не расходует право на meal-награду;
- исчерпанный предел не блокирует рецепты/готовку, не уменьшает заработанный XP
  и должен быть виден до выполнения следующего задания.

Это демонстрационное ограничение злоупотреблений, **не оптимизированная экономика**.
Предел выбран как минимальная защита для demo в рамках разрешения реализовать
план, а не как оценённая на реальных пользователях частота вознаграждения.

## 7. Метрики: не путать выполненное задание с дополнительной покупкой

- Показы, выбор задания, приготовление по заявлению и XP — диагностика игрового
  взаимодействия. Для `ready` отсутствие повторного открытия после покупки не
  считается незавершённостью: пользователь уже сделал явный выбор в игре.
- Вход после кассы может дать первый игровой результат, но предшествующую
  покупку нельзя приписывать игре. Отдельно записываем этот путь и планирование
  до следующей покупки, независимо от `current/repeat/explore`.
- Покупка в тот же календарный день может завершить задание, но не добавляет
  новый покупочный день. Сдвиг состава запланированной корзины — не рост частоты.
- Основная проверка остаётся test/control по покупочным дням и марже на
  участника. Ни начисленный XP, ни число сцен не доказывают причинный uplift.

## 8. Реализация API 1.3 и границы следующего шага

| Участок | Состояние |
|---|---|
| Backend / Safety | Реализовано: план связан с серверным оффером и подтверждёнными чеками; награды отделены от завершений; purchase-day XP и legacy-обход через `recipe_completed` убраны; предел применяется атомарно |
| Frontend / Product | Реализованы явный выбор задания, его название по стратегии, статус награды и текст завершения без XP; клиент не начисляет XP. Каталог отдельных обоев и UX цели/применения — инкремент C6 по ссылке выше; отдельные реакции по current/repeat/explore остаются вне него |
| ML / Recsys | Сохранить ADR-003 и объяснение стратегии; не подмешивать XP в relevance и не форсировать новый рецепт, бренд или уценку ради разнообразия; новый классификатор заданий не требуется |
| Eval / материалы | Разделить вход после покупки и план до покупки; обновить описание наград, demo-сценарии и ограничения; не объявлять новые гипотезы измеренным результатом |

HTTP-изменения относительно 1.2:

- `MealRecommendation.offer_id` выдаётся HTTP-сервером после safety/selector;
  offline-конструктор может оставить его пустым, но такой объект не активирует задание.
- `MealPlanSaveRequest.offer_id` обязателен. Сервер проверяет пользователя,
  recipe/route, полный выбор допустимых SKU, fulfillment и время выбора.
- `MealPlanSnapshot` содержит `offer_id` и `reward: {status, xp, purchase_day}`.
  Статусы: `awaiting_purchase`, `no_purchase_evidence`, `available`, `awarded`,
  `purchase_day_reward_used`. `xp` — доступный/выданный бонус конкретного задания,
  не общий баланс; фактический общий XP берётся из `progress`.
- `ProgressSnapshot.rewarded_meals` считает награждённые задания отдельно от
  `meals_completed`; save-ответ также возвращает `progress` для post-checkout ready.
- `recipe_completed` в legacy receipt-запросе читается, но не завершает блюдо и
  не награждает его; ответ объясняет это кодом `legacy_completion_ignored`.

Код: `app/meal_offer.py` — сверка с выданным оффером; `app/state.py` — проверенные
чеки, планы и атомарные записи наград; `app/progress.py` — повтор чека с актуальным
связанным планом; `mobile/src/domain/mealFlow.ts` — передача токена и тексты награды.
В мобильном demo текущий синтетический чек сначала явно проходит receipt endpoint;
сам recommendation-запрос не превращает историю в проверенную покупку.

Нельзя молча поменять смысл существующего `completed` на «XP выдан»:
завершённое блюдо может не иметь награды. У клиента должно быть явное объяснение
«ожидаем покупку», «нет подходящего покупочного подтверждения» или «лимит использован».
Повтор потерянного ответа восстанавливает серверное состояние без новой награды.

План проверки и публикации — [fixes and merge](../reviews/2026-09-06-fixes-and-merge.md).
Механические дефекты ревью исправлены отдельным коммитом; сами по себе они не
исправляли XP. API 1.3 требует совместного обновления клиента и сервера.

## 9. Приёмка нового правила

| Сценарий | Ожидаемый результат |
|---|---|
| Чек без игрового задания | Покупочный день учитывается, обычных покупочных/meal XP нет |
| Просмотр / сохранение рецепта / выбор задания без выполнения | 0 XP |
| `current`: выбран после подходящего подтверждённого чека, докупка не нужна, `cook` завершён | 20 XP при свободном лимите; лишнюю покупку не требуем |
| План до покупки: совпали все необходимые товары, затем подтверждена готовка | Однократно 20 XP |
| Готовка только из HOME без подходящего чека; повтор с новыми plan IDs | Личная история доступна, 0 XP во всех повторах |
| Посторонний товар, чужой/отклонённый чек, неподтверждённая история, выдуманный оффер, подмена route/SKU | Награда не выдаётся |
| Для плана продолжения использован старый чек | Не закрывает новую докупку; исключение текущего чека не применяется |
| Явно выбран `ready`, совпал купленный SKU, до или после выбора по допустимому пути | Однократно 20 XP, без заявления о готовке; без выбора задания 0 meal XP |
| Повтор completion/чека, потерянный ответ, конкурентные запросы, смена mode/new plan ID | Состояние восстанавливается; основание не награждается повторно |
| Несколько чеков одного московского дня; приготовление на следующий день; план из нескольких чеков | Лимит по покупочному основанию §6, без размножения бонусов и зависимости от порядка доставки чеков |
| Рецепт завершён без доступной награды | Счётчик завершений не превращается в XP; UI объясняет причину заранее |
| Успешный referral / повтор referral | Прежняя отдельная однократная награда сохранена |
