Статус: выборочная интеграция и локальные автопроверки завершены, 05.09.2026.
Ручной прогон на телефоне и финальный ML-eval ещё нужны. Точка входа для коллег, которым
нужно понять изменения без истории чата. Источник системных решений —
`experiment/vxofi`, API **1.2**, ADR-001–004. Новых продуктовых решений здесь нет.

Первая выборочная интеграция: **`1e55cd7`**. Следом подготовлено объединение с
`main@8be7a2d`, включающим `mobile@b948b37`; отличия описаны ниже.
Остаток до PoC — в [оперативном чеклисте](poc-readiness.md).

## Общий main: что добавлено после первой интеграции

Источник — `main@8be7a2d` / `mobile@b948b37`. Слияние сохраняет историю обеих
веток и системные решения API 1.2, а не возвращает legacy-клиент из mobile.

- Приняты уточнённый `/data/` ignore, исходники/спрайты и новая раскладка кухни
  с запасным рисунком при отсутствии подходящего. Подписи товаров остаются
  точными; рисунок может быть условным, это явно написано на экране.
- **Покупка наполняет кухню.** В `DemoContext` сохраняются `kitchenItems` и
  обработанные ID чеков; `domain/kitchen.ts` сопоставляет выбранные SKU с
  ингредиентом рецепта. Товар без сопоставления показывается под своим SKU,
  готовое блюдо — отдельной позицией, не набором сырых ингредиентов.
- От исходного `6c70677` отличается момент изменения: только после
  `verified/duplicate` от API. При `rejected/pending_review`, неизвестном статусе
  или сетевой ошибке кухня не меняется. Потерянный ответ восстанавливается
  повтором того же чека; известный чек второй раз не применяется.
- Корзина сохранённого плана остаётся для повтора запроса. После готовки
  упаковки автоматически не удаляются. Это история покупок текущей сессии,
  не серверный холодильник и не новые признаки наличия для recommender.
- При конфликтах сохранены наши meal-экраны, книга, «Мой план», ошибки,
  исправленная `KitchenSheet` и API 1.2. Старые `data/demo.ts` — только
  дизайн-референс; backend/ML от этого объединения не меняются.

Приёмка объединённого кода: **125 Python, 28 клиентских, 6 TS/API × 2 движка**,
TypeScript и Expo export web/iOS/Android. Новые пять клиентских регрессий
проверяют наполнение кухни, повторы/отклонения/сеть, ready и раскладку спрайтов.
CI предыдущего `1492019` прошёл; новая объединённая версия проверяется отдельно
перед merge. Успешный CI не заменяет ручной прогон на телефоне.

После слияния интеграционного PR командная база — `origin/main`; коллегам
передаём ссылку на **этот файл в main**. Автор продолжает работу в своей ветке.
Ниже сохранена карта первого переноса: она объясняет, почему часть старого
mobile/ML-кода намеренно не стала контрактом общей системы.

прогона на ней. Ссылки на исходные коммиты сохраняются для сравнения.

## Границы, которые важно не потерять

- «Приготовил» — `complete-cook`, не синтетический чек от имени пользователя.
- Покупка подтверждается выбранными SKU. Повтор запроса не даёт новые XP.
- Недавний чек не является точным холодильником или источником срока годности.
- Уценка — явный выбор; нет брони. Дом/работа — разные demo-расстояния.
- `current/repeat/explore` и порядок карточек определяет наш selector, не UI.
- Каталоговая пара «рецепт — готовый товар» не доказывает наличие и безопасность.
- Время/порции/кухня рецепта сохраняются как metadata, не требуют отката API.
- ML обучен на синтетике. Его подключение не доказывает 70% на людях или uplift.

## Что именно изменилось относительно исходных веток

### Frontend: `feat/mobile-app@4f374c3`

- Перенесены `KitchenScene.tsx`, `KitchenSheet.tsx`, `kitchenSlots.ts`,
  `kitchenPlacement.ts`, `productSprites.ts` и все 14 PNG из `assets/products/`.
  Сцена и позы сохранены; неработающая кнопка меню скрыта, пока нет обработчика.
- `KitchenSheet`: сохранённый `PanResponder` читает актуальные размеры и callback
  через ref. Раньше после `onLayout` жест оставался ограничен начальной высотой
  201; теперь ограничение обновляется. Есть также открытие кнопкой и обработка
  прерванного жеста. В нашей компоновке начальная граница — 221.
- `index.tsx` использует новую сцену, но вход перед доставкой и текущий meal-flow
  остаются нашими. `KitchenProduct` — отдельный тип отображения, без импорта
  старого локального каталога. Неразмещённые картинки не удаляют позиции из списка.
- `products.tsx`: маркировка уценки и зачёркнутая исходная цена взяты как приём
  оформления, но сами SKU/цены — из ответа API, не из `data/demo.ts`.
- Готовка: **план → «Начать готовить» → кухня с шагами → «Я приготовил» → сервер**.
  `DemoContext.confirmCooking()` возвращает успех/неуспех; переход к прогрессу —
  только при `completed/duplicate`. При ошибке можно повторить запрос.
  Фиксированный чек и удаление целых упаковок из «холодильника» не перенесены.
- Нижняя вкладка «Мой план» сохранена. В соседней ветке удалён старый «Каталог»,
  но в нашей этот маршрут уже обслуживает выбранный meal-план.

### ML: `experiment/recsys-benchmark@c28b613`

- Перенесены `catalog.py`, `recipes.py`, `model.py`, `pantry.py` и необходимый
  для импорта `data/price_reference.json`. Каталог: **47 рецептов, 98 ингредиентов**;
  scorer: логистическая регрессия с **16 признаками**, в том числе наблюдаемыми
  характеристиками истории и взаимодействиями пользователя с рецептом.
- `recipes.py`: `servings/dish_type/cuisine` сохранены в новом
  `recipe_metadata.py::RECIPE_METADATA`, не добавлены неоговорёнными полями в
  строгую API-схему. `quantity/unit/required` используют существующий контракт;
  `meal_intent_id=recipe_id` даёт стабильный ключ, но сам не создаёт ready-SKU.
- `model.py` и `pantry.py`: явно заданные продукты дома уменьшают докупку,
  но не превращают `explore` в `current`; готовое блюдо не разбирается на сырые
  продукты из его состава. В missing count/cost входят только обязательные
  ингредиенты. История покупок автоматически не превращается в остатки дома.
- Serving использует `DISABLED_PANTRY` и `include_effort_features=True`.
  Альтернативные настройки в классе — экспериментальные возможности исходника,
  не включённые решения продукта. Окончательный порядок и объяснения остаются в
  нашем service/selector, а не берутся напрямую из model reason codes.
- Наши `profiles.py`, `inventory.py`, `evaluation.py`, `simulation.py` и
  `economics.py` не заменены версиями из ML-ветки. Новая модель обучается при
  запуске на **наших** синтетических профилях с расширенным каталогом; это не
  воспроизведение всего benchmark коллеги.
- `recsys/examples/sample_recommendations.json` пересоздан текущим генератором:
  10 профилей проходят через настоящий `RecommendationService` и API 1.2.
  Это примеры recipe-выдачи, не лог кликов пользователя и не отчёт о causal uplift.
- `pyproject.toml` включает `recsys/data/*.json` в устанавливаемый пакет: иначе
  локальный editable-запуск работает, а wheel теряет обязательный price reference.

Не перенесены API 1.0, альтернативные ranking policies, CatBoost/benchmark,
историческая модель «истинного холодильника», LLM-аудит, ready-каталог как
источник наличия, калибровочные скрипты и старые отчёты. Агрегат цен — лишь
reference исходного эксперимента, не текущая цена в магазине. В API 1.2 нет
поля `price_is_estimate`; все наши inventory/мобильные цены явно демонстрационные.
Внешние датасеты, платные LLM-вызовы и новые ML-зависимости для serving не нужны.

### Что сейчас увидит человек в мобильном демо

Модель обучена на 47 рецептах, но **ранжирует каталог из запроса**. Мобильный
[`mealRequest.json`](../mobile/src/fixtures/mealRequest.json) пока содержит
одного фиксированного пользователя и три блюда: пасту с томатами, болоньезе и суп.
Истории чеков `purchase_history` в этом fixture нет: это также проверка cold start,
не демонстрация всех обучающих персон. `recipeDetails.ts` даёт шаги только для
этих трёх точных составов. Никаких локальных дополнительных карточек поверх API нет.
Продукты на рисунке начинаются с фиксированного недавнего чека и пополняются
принятыми API покупками текущей сессии. Это не меняет входные признаки
рекомендаций автоматически и не доказывает, сколько продукта осталось дома.

Чтобы расширить demo, нужно согласованно обновить профиль, recipe/ingredient IDs,
остатки обычных и ready-SKU, затем инструкции и тесты — не просто импортировать
47 названий в React. Каталог готовой еды без состава, срока и остатка в конкретной
точке не проходит вместо проверенного `InventoryProduct`.

## Как проверить после своих изменений

Backend из корня, после установки `python -m pip install -e '.[dev]'`:

```bash
.venv/bin/python -m pytest
.venv/bin/python -m recsys.generate_examples
git diff -- recsys/examples/sample_recommendations.json
```

Генератор **перезаписывает** tracked-пример; при неизменных model/data diff пуст.
После осмысленного изменения модели diff нужно просмотреть и сохранить, а не
отключать `test_committed_sample_artifact_matches_current_response_contract`.

Frontend из `mobile/`, Node 24, зависимости по lockfile:

```bash
npm ci --legacy-peer-deps --ignore-scripts --no-audit --no-fund
npm run typecheck
npm test
npm run test:api
X5_TEST_ENGINE=model npm run test:api
npm run export:check -- --max-workers 2
```

`test:api` запускает Python TestClient и настоящие TypeScript-сборщики, не HTTP
заглушку. В model-прогоне `/health` должен вернуть `model_fallback=false` и
`recommendation_engine=model`; незаметный переход на mock ломает тест.
Запуск приложения и сценарий ручной проверки — в [mobile/README](../mobile/README.md).

Локальный результат 05.09: **125 Python-тестов, 23 клиентских теста,
6 TS/API-тестов × 2 движка**, TypeScript и Expo export web/iOS/Android — успешно.
Новые регрессии: [`test_model_api12_integration.py`](../tests/test_model_api12_integration.py),
[`kitchen.test.mjs`](../mobile/tests/kitchen.test.mjs),
[`cooking-state.test.mjs`](../mobile/tests/cooking-state.test.mjs).
Также проверена одинаковая model-выдача в процессах с разными `PYTHONHASHSEED`.
CI дополнен model-прогоном; удалённый результат ещё не проверен.
Python wheel собран; из распакованного пакета вне рабочего каталога успешно
запущен `/health` с model без fallback и загружены все 47 рецептов.

Это тесты контрактов, бизнес-переходов и отдельных React-обработчиков с test doubles.
Expo export не является native build, автоматическим нажатием по экранам или
визуальной проверкой. Ручной прогон на телефоне остаётся открытым gate.

## Как продолжать в соседней ветке

1. Прочитать этот файл, [текущий статус](project-status.md) и ADR своего участка.
   После слияния интеграционного PR выполнить `git fetch origin`.
2. До слияния посмотреть `git log --oneline HEAD..origin/main` и
   `git diff --stat HEAD...origin/main`. Для конкретного файла
   полезно сравнение двух версий, например:

   ```bash
   git diff c28b613 origin/main -- recsys/model.py
   git diff b948b37 origin/main -- mobile/src/state/DemoContext.tsx
   ```

3. Сохранить свою незакоммиченную работу, затем в **своей** ветке интегрировать
   `origin/main`. Это не команда переключить всем ветку и не push в main.
   История mobile включена; ML переносился выборочно, поэтому merge его
   исходной ветки всё ещё может конфликтовать. Не разрешать конфликт заменой API/service/context
   старым файлом целиком; использовать карту адаптаций выше.
4. Прогнать проверки своего участка и оба TS/API smoke. Если меняется контракт —
   сначала согласовать решение и обновить ADR, затем код обеих сторон.

## Следующий шаг, не скрытая часть завершённого scope

- Совместный ручной прогон на телефоне и визуальная доводка новой кухни.
- С ML-участником — расширение mobile fixture/персон и повторный eval конечной
  API 1.2 выдачи на 30–50 профилях с baseline и разделением cooking/ready сегментов.
  Старые benchmark-числа и текущие тесты связности не заменяют этот deliverable.
- Поправка «закончилось», декор, UI рефералов и приватного ранга — отдельные задачи.
- Персистентность, реальные остатки/доставка и серверная привязка плана к ранее
  выданной рекомендации пока не реализованы. Не обещать их в демонстрации.
