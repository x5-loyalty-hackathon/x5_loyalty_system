# Промежуточная презентация — содержание слайдов

- **Статус:** готовый текст под сборку слайдов. Сам файл презентации собирает
  Product/UX owner и экспортирует в требуемый формат.
- **Объём:** 10 слайдов.

## Слайд 1. Титул

X5 Домовой — персональный игровой слой поверх программы лояльности.
Команда, кейс X5 Tech, промежуточная сдача 04.09.2026.
Одна фраза: «Чек превращается в персональные рецепты, а следующая покупка —
в личный мир Домового».

## Слайд 2. Проблематика

- В приложениях X5 есть чеки, баллы, промо и точечные механики — нет цельного
  персонального игрового слоя.
- Между покупками нет причины открыть приложение без конкретной скидки.
- Частота, купленная скидкой, оплачивается маржой.
- Вывод исследования: игровой слой сам по себе чаще растит app-retention, чем
  покупки.

## Слайд 3. Постановка задачи

- Сегмент: домохозяйства, регулярно покупающие ингредиенты для готовки.
- Три механики: рецепт-челлендж после чека, личный прогресс Домового, реферал.
- Primary метрика: `Δ уникальных дней покупок` и `P(дней ≥ N)` на 30/60 днях.
- Guardrail: contribution margin на пользователя не ниже контроля.

## Слайд 4. Выбранный подход

Нулевая гипотеза: ещё одна игра не даёт uplift сама по себе → игровой слой
надстраиваем над ежедневной полезностью «что приготовить из этой корзины».

Ключевой pivot: не физический rescue-бокс с бронью, а цифровой recipe plan с
опциональной уценкой. Снимает сборку, предоплату и no-show.

## Слайд 5. Схема решения

```text
чек → персональные рецепты (current / repeat / explore)
    → ингредиенты: куплено / дома / уценка / full-price / недоступно
    → доставка или следующий визит
    → новый чек → прогресс Домового и личная статистика
```

Архитектура: Frontend → FastAPI → `RecommendationEngine` (mock ↔ ML adapter)
→ детерминированный SafetyPolicy **после** модели → ответ с reason codes.
Правило: AI ранжирует, детерминированные правила разрешают.

## Слайд 6. Четыре экрана

Экран 1 «Что приготовить» · Экран 2 «Рецепт и ингредиенты» ·
Экран 3 «Мой план» · Экран 4 «Личная кухня».
Показать индикатор недостающих продуктов, состояния ингредиента и явное
предупреждение, что уценка не забронирована.

## Слайд 7. Выполненные этапы

- Исследование: X5 Клуб, российские и международные кейсы, экономика rescue.
- ADR-001, technical design, обязательный MVP и test gates.
- Backend: recommendation contract v1, mock-движок, safety policy,
  идемпотентные чеки, прогресс и приватный ранг, реферал, антифрод.
- CI на Python 3.11 и 3.14.

## Слайд 8. Первые результаты и демо

- **23 backend-теста проходят** (safety, идемпотентность, fallback, антифрод).
- Сервис поднимается локально, example request возвращает ≤3 безопасных
  рекомендации с reason codes.
- Демонстрация: запрос → ответ с состояниями ингредиентов → чек → прогресс.

Честно не заявляем: обученную модель, измеренный hit rate, симуляцию 1–10k и
причинный uplift.

## Слайд 9. Риски и ограничения

- Уценка не бронируется и может закончиться до покупки.
- Full-price fallback может вырождать rescue в обычную витрину.
- Доставка может лишь переносить покупку между каналами.
- Mock вместо модели; состояние в памяти процесса.
- Пороги антифрода и константы XP — demo-значения, требуют review.
