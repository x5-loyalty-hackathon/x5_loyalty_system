# API для будущих продуктовых дашбордов

Статус: реализован **демонстрационный read-only API**, не сам дашборд и не
результаты реального пилота. Данные — синтетический ledger текущего процесса;
перезапуск сервера / reset очищает историю. Ничего не подключено к данным X5.

## Ручки

```text
GET /api/v1/metrics/summary?start_date=2026-09-01&end_date=2026-09-06&purchase_threshold=2
GET /api/v1/metrics/daily?start_date=2026-09-01&end_date=2026-09-06
```

- `start_date` и `end_date` обязательны, обе даты включены, календарь
  `Europe/Moscow`; максимум 366 дней. Невалидное окно → HTTP 422.
- `purchase_threshold` — N для доли пользователей с ≥ N покупками / днями с
  покупкой; только summary, по умолчанию 2, допустимо 1–1000. Это параметр
  запроса, **не утверждённый критерий успеха пилота**.
- Необязательный `cohort=cooking_households|ready_heavy` отделяет сегменты.
  В PoC метка берётся из **первого принятого чека**, прислана демо-клиентом,
  не является результатом валидированного сегментатора. До первого чека
  сегмент неизвестен: пользователь учитывается без фильтра, но не попадает
  ни в один сегмент при фильтрации. Текущая известная метка применяется ко
  всему окну; исторической сегментации на момент каждого события пока нет.
- OpenAPI со схемами ответов: `/docs`, `/openapi.json`. Контракт основного
  пользовательского API не меняется: это дополнительные GET.

Оба ответа содержат `window`, `metadata` с ограничениями и доступностью метрик.
Summary содержит `counts` и `purchase_frequency`; daily — `days`, по одной
записи `{date, counts}` на каждый день, включая нулевые дни.

## Что именно считаем

| Поле | Определение |
|---|---|
| `observed_event_users` | Уникальные пользователи хотя бы с одним сохранённым событием в окне: принятый чек, выданный meal offer, создание или завершение плана. Это наблюдаемая событийная аудитория, **не все назначенные в тест пользователи**. |
| `unclassified_event_users` | Из наблюдаемых пользователей — ещё без первого принятого чека / известного сегмента. |
| `verified_receipts` | Число уникальных принятых чеков по `receipt_id`. Повторы, чужие повторные отправки, rejected / pending_review не добавляют чек. `current_receipt` и history в запросе рекомендаций сами по себе не являются принятыми чеками. |
| `purchasing_users` | Уникальные владельцы принятых чеков в окне. |
| `purchase_user_days` | Число уникальных пар `(пользователь, московская дата покупки)`. Два чека за день — два чека, но один покупочный день. |
| `receipt_amount_rub` | Сумма `quantity × unit_price` принятых чеков, до округления общего результата до копеек. Это сумма товаров в чеках, **не инкрементальная выручка и не маржа**; возвраты не представлены. |
| `markdown_savings_rub` | По уценённым строкам: сумма `quantity × (original_unit_price − unit_price)`. Это экономия покупателя относительно указанной старой цены, не стоимость списаний и не прибыль компании. |
| `meal_offers_issued` | Количество объектов meal offer, действительно выданных сервером. Один ответ может содержать несколько offers; повторный запрос может выдать новые. **Это не показы карточек и не число запросов.** |
| `cook_plans_created`, `ready_plans_created` | Принятые уникальные планы по дате создания, с разделением маршрутов. Retry того же плана не добавляет событие. |
| `cook_plans_completed`, `ready_plans_completed` | Уникальные завершённые планы по дате завершения. Cooking — пользователь подтвердил готовку; ready — подходящий принятый чек. Домашняя готовка без подтверждённой покупки может завершиться с нулевым XP. |
| `rewarded_completed_plans`, `meal_xp_earned` | Завершённые планы с реально выданной наградой и сумма их XP. Дата — **завершение**, а не дата покупки, ограничивающая дневную награду. Пассивная покупка и сохранение плана XP не дают. |

`purchase_frequency` использует **один явный знаменатель**:
`counts.observed_event_users` за всё выбранное окно и сегмент:

- `receipts_per_observed_user` = чеки / наблюдаемые пользователи;
- `purchase_days_per_observed_user` = покупочные user-days / наблюдаемые пользователи;
- `users_at_least_n_receipts` и `users_at_least_n_purchase_days` — числители;
- `share_at_least_n_receipts` и `share_at_least_n_purchase_days` — соответствующие
  доли **от 0 до 1**, не проценты. При пустом знаменателе доли и средние — `null`.

Это позволяет отделить дополнительный чек от дополнительного покупочного дня
и активность игры от покупок. Но знаменатель зависит от взаимодействий с PoC:
он **не пригоден для оценки ITT-эффекта**. До пилота нужны отдельный полный
список назначенных участников, рандомизация, контроль и доверенная телеметрия.
Запрос с пустой выдачей не создаёт offer и **не добавляет пользователя** в этот
знаменатель; действие только с книгой рецептов также не имеет датированного
события. Поэтому это не все посетители или все запросившие рекомендации.

Daily: чеки, user-days, планы и XP можно суммировать по дням. Число уникальных
пользователей **суммировать нельзя**: один человек встречается в нескольких
днях. Денежные значения округляются на уровне возвращаемого периода; сумма
округлённых дневных значений может отличаться от общего значения на копейки.

## Что намеренно не выдаём за измеренное

В `metadata.unavailable` возвращаются причины недоступности:

- причинный uplift / частота на назначенного участника — нет экспериментального roster;
- маржа, ROI, эффект каннибализации — нет себестоимости и причинного прироста;
- показы, открытия, игровые retention / conversion — нет клиентского event ledger;
- реферальный XP **за период** — награды сохраняются без временной метки;
- fraud-rate / precision — нет истории отклонённых решений и проверенной разметки;
- сохранения в книгу **за период** — книга хранит множество без дат сохранения.

Создания и завершения планов здесь — **событийные счётчики, не последовательная
воронка**. План мог быть создан до окна, а завершён внутри: делить такие
завершения на создания этого окна как conversion неправильно. Серверные offers
также нельзя подменять реальными показами интерфейса.

Все даты — **синтетические business timestamps из демо-контрактов**:
`receipt.purchased_at`, `request.now` для offer, `plan.created_at/completed_at`.
Это не production trusted ingestion clock; ретроспективные события и новые
метки сегмента могут изменить повторно запрошенный исторический срез.

## Реализация и проверки

- `app/state.py::metrics_snapshot` атомарно копирует только нужные данные под
  общим lock, не регистрирует пользователей и не вызывает reward-mutating helpers.
- `app/metrics.py` считает агрегаты по копии; `app/main.py` публикует две GET-ручки.
- `tests/test_metrics_api.py`: пустые окна / `null`, границы Moscow, дедупликация,
  rejected/review, разные сегменты, неизвестные сегменты, cook/ready, дневной
  лимит XP, дата завершения против даты покупки, отсутствие PII и побочных эффектов.

```bash
.venv/bin/python -m pytest tests/test_metrics_api.py
```

Ответы содержат только агрегаты, без user ID, receipt ID, магазинов и состава
чеков. **Production authorization не реализована**, как и у остальных PoC
ручек: не открывать этот API с реальными данными. До пилота понадобятся
авторизованный аналитический доступ, persistent ledger и правила приватности.
